# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. Read the **Domain rules** and **Workflow conventions** sections before touching any import, transaction or stats code.

## Product vision

**Finances** is a single-user, self-hosted personal finance tracker. The owner imports bank CSV exports and statements; transactions are parsed, deduplicated, normalized and categorized automatically. Dashboards show:

- all accounts and net worth;
- monthly income, expenses and savings;
- budget vs target per category;
- subscriptions and fixed costs (auto-detected recurring transactions);
- savings and investments (PEA, life insurance, employee savings, crypto);
- an end-of-month forecast.

It is prototyped locally first, then deployed on a VPS and used from the phone as a PWA, ideally reachable only through Tailscale. There is exactly one user: no public sign-up, no multi-tenancy, no third-party analytics.

## Domain rules

These rules are non-negotiable. Code, tests and reviews must enforce them.

### Money and dates

- Money is stored as **integer cents** (`bigint` / `integer` columns), never as floats. Currency is **EUR**.
- Parse amounts from strings directly into cents (e.g. `"1 234,56"` → `123456`); never go through `parseFloat`. Convert to a decimal representation only at the display edge (e.g. `Intl.NumberFormat('fr-FR', { style: 'currency', currency: 'EUR' })`).
- Transaction dates are **calendar dates** (`date` columns / `YYYY-MM-DD` strings), not timestamps. Never shift them through a time zone conversion.
- The app time zone is **Europe/Paris**. Anything that depends on "today" or "this month" (month boundaries, forecasts) is computed in Europe/Paris.

### Transactions

- Every transaction has a `kind`: `expense`, `income` or `transfer`.
- Moves between the user's own accounts (e.g. checking → Livret A, checking → PEA) are `transfer` and must **never** count as income or expense in any statistic, budget or forecast.

### Recurring items (Abonnements)

- `recurring_items` are series found by the detector (`apps/api/src/recurring/detect.ts`, one per account + merchant key + direction; transfers and one-offs never count): `suggested`, `confirmed` (a real recurring item) or `dismissed` (not one, never suggested again). A detection run refreshes the stats only, never the user's columns (`name`, category, fixed-cost flag, cadence override, `notes`, `status`, `ended_on`). A series without a charge for `STALE_PERIODS` (1.5) periods is inactive.
- **Cancellation** (« Résilier », #270) is an end date, not a status: `recurring_items.ended_on` is the **first day no charge is expected any more** (past, today or future), on `confirmed` items only (`PATCH /api/recurring/:id` with `endedOn`, `null` reactivates; 400 on other statuses; refused to access tokens: 403, so the MCP never cancels). The DTO carries `endedOn`, `ended` (`endedOn` ≤ today in Europe/Paris) and `chargedAfterEnd` (latest occurrence booked on or after `endedOn`, a cancellation that did not go through; the end date is never cleared automatically). From `ended_on` an item is out of the forecast and the expected costs (`expectedOccurrences` expects nothing on or after it), and once `ended` out of the yearly / fixed-cost / « Abonnements » totals (`summary`, `endedCount`) and the upcoming debits; before it, it counts as usual. The web shows « Résilié · fin le … » in its section until then, then « Abonnements résiliés » (collapsed, opened when one was charged after its end), with « Réactiver » and « Modifier la date » in the editor; « Résilier » (`EndRecurringSheet`: « Aujourd'hui », « Après la prochaine échéance », any date, note) is for debits only, and every change's toast offers « Annuler ».

### Month comparisons

- Statements are imported by hand, so the current month is often empty or partial. Every page that compares months (dashboard, spending, savings, budget) goes through `apps/api/src/coverage/`: `dataUntil` is the latest booked transaction or committed import end (per account, overall = the latest of them), never after today in Europe/Paris; a month is `complete`, `partial` (first `throughDay` days known) or `empty`.
- A partial month is compared **like for like**: the same first days of the previous month and of the averaged months. An empty month is not compared at all. Without a `month` parameter, endpoints show the current month when it has data, else the month the data stops in. Responses carry a `period` (`MonthPeriodDto`) and the web states it with `PeriodNote` (`lib/period.ts`). Every month page (dashboard review, Dépenses, Opérations, Budget, Épargne, Revue du mois) moves between months with the shared `MonthNavigator` (`components/month/`, #213): previous / next, ← / → on a keyboard, the month name opening a picker with the months that have transactions marked and shortcuts to the current month and to the month the data stops in, from `GET /api/coverage` (`dataUntil`, `defaultMonth`, `months`). It is the first row under `PageHeader`, in `MonthToolbar` (#263, the owner's « proposition A »): one bar across the page (`bg-card`, border) holding the navigator, then the page's filters (`filters(layout)`) and actions at the end of the row, and its `PeriodNote` at the bottom (never a `PeriodNote` placed by hand with a negative margin). The bar is the navigator's container: below 672px of width the filters fold behind a « Filtres » button (bottom sheet, with the number of filters set, `activeFilters`) and the actions get a row of their own. A page with neither gets the `PeriodNote` at the end of the navigator's row (below it on phones), and a lone navigator gets no bar at all. The navigator's box (‹ | month | ›, no ⌄, 44px, `PeriodStepper` in `@finances/ui`) fills its row below 672px of bar width (up to « Filtres » or the bar's edge, the label growing between two 44px arrows: no empty space, the owner's choice) and keeps its own width from 672px, with the short label « oct. 2026 » in bars under 420px and the label as wide as the year's widest month so the arrows never move. Opérations (#264) puts its search in the navigator's row (`search` slot: the rest of the row from 672px, a row of its own below the month on phones) and its filters as chips under it (`FilterChip` / `ToggleChip` in `components/transactions/`: « Compte ⌄ » unset, « Compte : Livret A × » set, a popover of options, categories searchable; « Effacer » only when one is on; on phones only the chips that are on, the rest in the « Filtres » sheet), « Toutes les dates » in the navigator's picker (`allDates`), one totals strip Revenus · Dépenses · Net (only Net toned, `chart-delta-*`) and the count, « Tout sélectionner » and the sort in the list header; the URL search params are unchanged. The default month stays out of the URL; the sidebar links carry `?month=` between Dépenses, Opérations, Budget, Épargne and Revue du mois.
- The end-of-month forecast (`apps/api/src/forecast/`, `GET /api/forecast`, #215) projects from the day after `knownUntil` (the selected accounts' `dataUntil`, the latest of them), never from today: recurring items (none on or after a cancelled item's `ended_on`) and the day-to-day estimate fall on their own dates, and the day-to-day expenses entered by hand since then (already in the balance) replace the estimate of the elapsed days (`coveredCents`), so nothing counts twice. Data more than `FORECAST_STALE_AFTER_DAYS` (7) days old (or none) makes it `stale`: indicative, `belowThreshold` null (no low-balance alarm), and the page offers « Importer un relevé » / « Ajouter une dépense ».
- The dashboard is read once a month: it opens on the review of the previous calendar month (`GET /api/dashboard/review`, `MonthReview`, #262, the owner's direction « A. Tuiles », prototypes in `apps/ui-docs/src/prototypes/dashboard.stories.tsx`): the `MonthNavigator` heads the card with « Clôturé » / « À clôturer » (`closedAt`, from `month_closes`; `closed` only means every account is up to date), then the accounts not updated up to the month end (cash: data stops before it and no import committed after it, opening the import; investments: no value on or after it, opening the account page), income / expenses / saved (rate) as three figures, the net worth at the month end with its change only when investments or anything else moved it (otherwise it equals what was saved), the budget's target as a bar with what's left and the 2 categories furthest above and the 1 furthest below their target, and one action from the month's state: « Revue et clôture » while it is open, « Préparer le budget du mois suivant » once closed if the next month has none (`nextMonthBudgeted`), else a « Revoir le mois » link. Every amount is shown once and the month named once. The dashboard has one card per row (owner's choice: review, Ce mois-ci, Fin de mois, Comptes, Revenus et dépenses), read top to bottom in full-width strips, never two columns inside a card (owner's « Bandeaux »): from `@[36rem]` the review's four figures (income, expenses, saved, net worth at the month end) sit in one row and the budget on one line (target, long bar, what's left), each envelope takes one line (long bar, what's left at its end); the accounts stay one full-width list with the add buttons one per line at full width. Every dashboard card uses `DashboardCardHeader` (title, optional status, at most one « Voir … › » link); today's net worth is only in « Comptes » (« Patrimoine à ce jour », « Évolution » to `/net-worth`, no net-worth chart on the dashboard).

### Month-end review (closing a month)

- The guided "Revue du mois" (`/month-review`, `apps/api/src/month-close/`, `GET|PATCH /api/month-close/:month`) computes its steps from existing data: imports up to date per cash account (the month review's missing accounts, missing days, running-balance gaps from the stored bank rows, manual transactions excluded), the month's review queue, recurring items (no `suggested` left; the month's price changes and cancelled items charged during the month on or after their end date, `chargedAfterEnd`, ticked as seen), budget and savings (ticked as seen), investment values at the month end, then the close. Only `recurring`, `budget` and `savings` are ticked by hand (`month_closes.acknowledged`).
- `POST /api/month-close/:month/close` (months before the current Europe/Paris month only) freezes the report (flow, net worth at the month end, savings target, totals per category with the month before and targets, largest one-offs, notes) in `month_closes.report`; later edits show as `changes` against the live report. A closed month refuses ticks and notes until `POST .../reopen`, which drops the frozen report and keeps the notes. Closing and reopening are session-only (never `@TokenAccess('write')`).

### Accounts

- Account types: `checking`, `savings`, `brokerage` (PEA), `life_insurance`, `employee_savings`, `crypto`.
- **Transactional accounts** (checking, savings) are fed by imports; their balance comes from transactions.
- **Investment accounts** (brokerage, life_insurance, employee_savings, crypto) are tracked by **dated value snapshots**. For crypto, the value can also be derived from holdings × price.

### Crypto prices

- Crypto accounts hold **holdings** (`crypto_holdings`: asset, location label such as a wallet or exchange, quantity, optional invested cents). Quantities (`numeric(38, 18)`) and EUR prices (`numeric(38, 12)`) are **exact decimal strings** handled with the BigInt helper in `apps/api/src/crypto/decimal.ts`; never `parseFloat` them. Value = round half to even of quantity × price, in cents.
- Prices come from a key-less public API (CoinGecko `simple/price`, behind the `PriceProvider` interface), **server-side only**, all assets batched in one request, cached in `crypto_prices` for `PRICE_CACHE_TTL_SECONDS` (default 600) and kept as last known price when the API fails (flagged stale, never a 500). `PRICE_API_ENABLED=false` disables it: only manual prices (`PUT /api/crypto/prices/:assetId`) are used.
- **Privacy**: the price API only receives asset ids (and the asset search text), never quantities or values. Never log quantities, prices × quantities or values.
- Valuing an account upserts **today's** `balance_snapshot` (Europe/Paris), so balances and net worth use the normal snapshot path; there is no separate crypto net-worth path. A **first** value of 0 € (lines at 0, nothing synced yet) is not recorded: the account stays "not valued yet" (#207).
- A crypto account has a **source** set at creation (`accounts.crypto_source`): `exchange` (with `crypto_provider` binance / coinbase / other; holdings from its imported exports), `wallet` (public keys in `crypto_wallet_keys`: Bitcoin xpub / ypub / zpub, a single Bitcoin address `1…` / `3…` / `bc1q…` / `bc1p…`, or EVM `0x` address, with the chains to read; holdings from the chain) or `manual` (typed by hand; accounts created before sources). A `manual` account holding nothing can become an exchange or a wallet once (`PUT /api/accounts/:id/crypto-source`, session only, #207; « Relier à un wallet ou une plateforme » on its source card, `ChangeCryptoSourceSheet`); its 0 € values are dropped when it never had another one. `GET /api/crypto/settings` says whether prices and wallet sync are on, so the wallet forms warn when sync is off. Holdings carry an `origin` (`import`, `sync`, `manual`): imported and synced lines are read-only and imports / syncs only replace their own lines, never manual ones. A `wallet` account takes no line typed by hand (#269): `POST|PUT /api/accounts/:id/holdings[/:holdingId]` answer 400 (`Wallet holdings come from the chain`) for it; lines typed before stay listed and can only be deleted. Public keys are validated before they are saved (`crypto/wallet-keys/public-key.ts`: base58check, bech32 / bech32m, EIP-55; private keys, WIF, recovery phrases, descriptors and testnet refused, each with its own message; the web form adds « Où trouver ma clé ? » per wallet), unique across accounts, reachable only with the session (`@TokenAccess('none')`), and never logged or sent anywhere but the wallet sync.
- **Wallet sync** (`apps/api/src/crypto/wallet-sync/`, #129, [ADR 0002](docs/adr/0002-wallet-sync-privacy.md)): opt-in (`WALLET_SYNC_ENABLED`, default `false`: no chain client is even built). Bitcoin addresses are derived on the server (`@scure/bip32`, BIP44 / 49 / 84, receive and change branches, strict gap limit 20, cached in memory) in the key's `address_types` (#248: `ypub` / `zpub` their own; an `xpub` the type chosen by the owner, default native SegWit, since Ledger Live exports `xpub` for every account, or detected on the first sync from the first receive address of each type, `detect_address_types`; keys saved before #248 keep their prefix type; `PATCH /api/accounts/:id/wallet-keys/:keyId` changes an xpub's type), a single address is read as it is, and both are read from Esplora (`ESPLORA_URL`, `BitcoinChainProvider`); EVM native and `balanceOf` token balances through JSON-RPC per chain (`EVM_RPC_URLS` keyed by chain id over the publicnode.com defaults, `eth_chainId` checked, `EvmChainProvider`). Tokens read = "Ajouter un jeton" only (`crypto_wallet_tokens`, `/api/accounts/:id/wallet-tokens`; manual lines no longer make the sync read their asset, #269): found by name (price id, contracts and decimals from CoinGecko `coins/:id`, `TokenContractProvider`) or by contract address and chain (#269: `decimals()`, `symbol()`, `name()` read with `eth_call` through `EvmChainProvider.tokenInfo`, only the contract sent, EIP-55 checked; stored with `chain`, `contract`, `decimals` and the asset id `erc20.<chain id>.<contract>`, `contract-assets.ts`, which is never sent to the price API and whose line, « sans cours », does not hold the account's valuation back). A sync replaces the account's `sync` lines (one per asset and chain, the chain label as location), sets `crypto_synced_at`, and runs before valuations (at most every `WALLET_SYNC_INTERVAL_SECONDS`) and on "Synchroniser" (`POST /api/accounts/:id/holdings/sync`, session only, at most every 30 s); each chain is read on its own (#250): a failing chain keeps its last lines (by location) while the others are replaced, sets `crypto_sync_failed_at` (stale), never a 500, and is named in `sync.failedChains` (chain, reason, `retryAt`; kept in memory). A 429 backs the chain's endpoint off in memory (`ProviderBackoff`: the larger of `Retry-After` and 1 min doubled per rate limit in a row, capped at 1 h): no request to it from page loads or "Synchroniser" until it ends (`sync.retryAt`, « Prochain essai possible à … »). **Bitcoin scans are resumable** (#268, `wallet-sync/bitcoin-scan.ts`): `crypto_bitcoin_scans` (per key and address type: `pass_started_at` while a pass runs, `completed_at`) and `crypto_bitcoin_scan_addresses` (branch, index, used, balance in sats, `read_at`; never the address, derived again) keep every address read; a pass reads the used addresses and the gap window after the last used one per branch, skipping what it already read since `pass_started_at` (a pass over 6 h old starts over), stores its reads even when a failure cuts it short, and the chain stays failed (its line kept) until the pass completes; a single address is a scan of one address. Page loads (`syncDue`) reuse a scan completed under `WALLET_SYNC_INTERVAL_SECONDS` ago (no request) and wait at most 5 s (`BACKGROUND_SYNC_WAIT_MS`) for the syncs they start, which go on in the background and value their account once done (`onLate`, #269); "Synchroniser" rescans every key and waits, except the keys completed during a Bitcoin read that failed (it resumes). Esplora is paced at one request per second (`ESPLORA_MIN_INTERVAL_MS`, 1000) and a `Retry-After` ≤ 60 s (none: 10 s) pauses the scan once per sync. `WalletKeyDto.scans` gives each type's used addresses after a complete pass (0 on an xpub: wrong type). Only addresses and token contracts are sent; logs carry the chain id, the failure reason and line counts only.
- A **wallet account's page** (#269, `components/crypto/WalletAccount.tsx`) is status → holdings → keys and tokens → history, each figure once: the value and « Soldes lus il y a … » or one line per chain not read (with its retry time) at the top, a single « Actualiser » page action (`POST .../holdings/sync`, which reads the chains then forces the prices; prices only when the server does not sync), no « Ajouter un avoir » (nor on its Crypto page card, nor in the Crypto page's account picker), no contribution tiles or « Versements inconnus » (`PerformanceTiles` `withValue` / `withContributions`), the holdings beside the keys and tokens from `@2xl`. Holding rows show the place only when it is not the asset's name and the origin badge only when the list mixes origins, next to the symbol. Each Bitcoin key says what its last scan found (« 4 adresses utilisées », or « Aucune adresse utilisée en Legacy (1…) : vérifiez le type » with « Changer »).
- The **Crypto** page (`/crypto`, `components/crypto/CryptoPage.tsx`) shows every open crypto account (one per exchange or wallet) from `GET /api/crypto/summary`; `POST /api/crypto/valuate` refreshes them all with one batched price request. `HoldingEditor` without an `accountId` lets the owner pick the account or set up a new one (`CryptoSourceFields` with `withSource`, shared with `AccountEditor`): a wallet asks for its public keys (several, e.g. a BTC xpub and an EVM address; each card is removed with the trash icon in its header, « Annuler » in the toast puts it back, #249) and no asset or quantity, then opens its page (sync, keys); an exchange asks for its provider, then opens « Importer un export »; « Saisie manuelle » creates the account with its first holding in one step (#207).
- **Exchange imports** (#128, `apps/api/src/imports/crypto/`, `POST /api/accounts/:id/crypto-imports` → `POST|GET|DELETE /api/crypto-imports/:id[/commit]`): Binance and Coinbase "Transactions" CSVs, detected from their headers (Binance French or English; Coinbase's preamble with the holder's name and user id is skipped unread, as are notes, remarks and addresses). Same model as bank imports: a pending preview (new / already imported lines, unknown operation types, tickers without a price id, the holdings after the import), nothing written before the commit, dedupe hash with an occurrence index among identical lines of the file (`dedupe.ts`), bad lines reported. Lines become `crypto_movements` (signed exact quantity, kind, EUR amount when exported); the commit replaces the account's `import` holdings with their sum per price id (`holdings.ts`: fiat left out, `transfer_internal` ignored, renamed tickers merged through `assets.ts`, invested = EUR cost incl. fees when the export gives it, unknown otherwise) and never touches manual lines. Tickers outside `assets.ts` are looked up with the asset search (ticker only) or chosen by the owner, and saved in `crypto_asset_aliases`. Session-only routes.

### CIC CSV import format

The first supported bank is CIC. Its CSV export:

- uses `;` as separator;
- is encoded in **Windows-1252** (decode explicitly, do not assume UTF-8);
- uses a comma as decimal separator;
- uses `dd/mm/yyyy` dates;
- has the columns `Date` / `Date de valeur` / `Débit` / `Crédit` / `Libellé` / `Solde`, where `Solde` is the running balance after the row.

The running balance is used to **check continuity** (previous balance + amount = new balance, within a file and across imports) and to rank probable duplicates between sources; it is not part of the dedupe hash.

### Imports

- Imports are **idempotent**: re-importing a file, or a file whose period overlaps a previous import, must not create duplicates.
- Legitimate identical transactions on the same day (same date, amount and label, e.g. two identical card payments) must be **kept**. The dedupe hash includes an occurrence index among identical (date, amount, normalized label) rows in file order, so they stay distinct and a re-imported file still matches. Rows from different sources (e.g. the spreadsheet history vs a CSV export) are compared by a fuzzy probable-duplicate check and shown as conflicts in the preview, never dropped automatically. See `apps/api/src/imports/dedupe/dedupe.ts`.
- Every import goes through a **preview** (new / duplicate / conflicting rows, continuity check) before it is committed. Nothing is written until the user confirms.

### Envelopes and manual transactions

- A budget line can be **tracked** (`budgets.tracked`, "suivre pendant le mois", carried over like the note): the dashboard's "Ce mois-ci" card (`GET /api/budgets/envelopes`, current Europe/Paris month) shows spent / target, what's left and the even-pace mark (target × day / days in the month).
- **Manual transactions** (`POST|PATCH|DELETE /api/transactions/manual`, `ManualTransactionsService`, #137 then #74) are transactions of any kind (expense, income, transfer) with `manual = true`, no import and a random `manual:<uuid>` dedupe hash: positive `amountCents` + `direction` (`out`/`in`, default `in` for income), optional category (without one: review queue, label required), day (never in the future), label, account (open checking/savings), one-off flag, note. They count in statistics and budgets at once, and in account balances from the day after the bank anchor (they never date the balance), but never as imported data: `coverage/` (`dataUntil`) ignores them and the import dedupe (`loadExistingForRange`) leaves them out. The web enters them with `ManualTransactionSheet` (transactions page "Ajouter une opération", dashboard envelopes). The sheet goes in three steps (#245, owner's choice: one decision per screen, « Suivant » / « Retour »): **Catégorie** (kind, a transfer's sign, « Habituels » tiles of usual labels with their category, every category of the kind as wrapping chips; a tap moves on), **Montant**, **Détails** (« Aujourd'hui » / « Hier » / date chips, label, « Plus d'options »: account, sign, one-off, note) then « Ajouter ». An envelope opens at the amount, an edit at the details. Usual labels come from `GET /api/transactions/manual/suggestions?kind=` (labels typed on manual transactions over a year, counted double, and merchants of imported rows seen twice in six months, each with the category filed ≥ 70 % of the time; plus the kind's most used categories over 90 days, the first being the default, #196). On phones (`useIsMobile`) it is a bottom sheet of one height whose amount is typed on its own keypad (`AmountKeypad`, `amount-entry.ts`: exact text, never a float), « Suivant » a key of it: the system keyboard never opens for the amount, and the footer steps aside while the label or note is typed (no button floating above the iOS accessory bar). Elsewhere a dialog: the amount is typed in its field and Enter moves on, then adds. Prototypes of the directions considered are Storybook stories (`apps/ui-docs/src/prototypes/`). Every control is 44px high. Date inputs drop their native look and sheets clip horizontal overflow (`packages/ui` `Input` / `Sheet`), so nothing pans sideways on iOS.
- **Reconciliation** (`apps/api/src/imports/reconcile/`): a `new` import row with the same account and amount, booked at most 5 days from a manual transaction, replaces it on commit (one to one, closest first), keeping its category, kind, note (or typed label), one-off flag and split; the preview shows the match. Unmatched manual transactions of the file's period (up to 5 days before its end) stay and are flagged for review. The commit re-matches against the manual transactions as they are then.

### Hand edits (#74)

- **Imported rows** stay editable for category, kind, flags and note (`PATCH /api/transactions/:id`). Their amount and date change only through "Modifier une opération importée" (`PUT|DELETE /api/transactions/:id/correction`): the bank values are kept in `original_amount_cents` / `original_booking_date` and read through `bankAmountCents` / `bankBookingDate` (`transactions.schema.ts`) by everything that is bank data (balances, continuity checks, `coverage/`, the dedupe of later imports, month-close gaps), so a re-import never duplicates or overwrites a correction and the dedupe hash never changes. Statistics use the corrected values.
- **Splits** (`transaction_splits`, `PUT|DELETE /api/transactions/:id/splits`): 2–20 parts, each with the transaction's sign, summing exactly to its amount in cents; the transaction keeps the category of its largest part for display. Per-category statistics (spending, budgets and envelopes, month-close totals, savings flows, `GET /transactions/summary`) read the `transaction_lines` view (one line per part, else the transaction), so a split counts in each category. A category set for the whole transaction ends its split; a split transaction's amount is locked until the split is removed.
- **Web**: a transactions row (#266, `TransactionRow.tsx`) is the category's icon in its colour (`CategoryAvatar`, a check when selected: tapping it selects the row, a warning dot when to review), one label (`displayLabel`; the raw bank label under it only when it says more, `secondaryLabel`), the category, the account only when there are several open accounts and the list is not filtered to one, small flag icons with an accessible name (ponctuelle, saisie à la main, corrigée, note; « À revoir » is the only text badge) and the amount (`Amount`: income green with « + », expenses in the text colour, internal transfers muted after ⇄; red is kept for what is wrong). Phones stack it on two lines; wide pages (`@xl` container) put the category (`CategoryMenu`: its name as text, opening the categories by kind) and the amount in columns, the account from `@2xl`, with no column headers. On wide pages the category and the amount of manual rows are edited in place. Activating the label opens the row's editor (#280, `TransactionEditor.tsx`; a bottom sheet on phones, a right-hand sheet on wide pages): a settings list, the frequent settings first (Catégorie ›, Note ›, Ponctuelle and À revoir switches saved at once), the rarer ones below (Répartir ›, Corriger montant ou date › for bank rows or Modifier ou supprimer › for manual ones, Type ›); each › opens its own screen with « Retour » (the category as icon chips by kind with a search, the note with « Enregistrer », the split, the correction, the type). The list has no keyboard shortcuts (#265): its controls are reached with Tab and used like any button or select. Every edit shows a toast with "Annuler" (`use-transaction-actions.ts`).

### Spreadsheet history import (one-shot)

The owner's pre-app history (a Google Sheet, ~3,250 categorized rows since 07/2023) is imported once from its CSV exports with `pnpm --filter @finances/api import:history` (code in `apps/api/src/imports/history/`, entry `apps/api/src/database/import-history.ts`; `node dist/database/import-history.js` where `tsx` is missing).

- **Dry run by default**: everything runs in one DB transaction that is rolled back unless `--commit` is passed. It prints counts only; `--report <path>` writes a detailed JSON report (merchant keys, line numbers, conflicts) and refuses any path inside the repo outside `data/`.
- **Inputs**: `Transactions` tab (`Date,Mois,Compte,Libellé,Montant (€),Catégorie,Groupe,Relevé,Ponctuel`, UTF-8, `,`-separated, `-1 234,56 €` amounts) and optionally the `Soldes` tab (`Fin de mois` + one column per account) → `balance_snapshots` on the last day of each month, upserted on (account, date). Columns are matched by name; bad rows are reported, never fatal.
- **Mapping** (`history/mapping.ts`): sheet category slugs → seeded slugs; the kind comes from `Groupe` (`Mouvement` → transfer, `Revenu` → income, `Dépense` → expense) and wins over the category's kind. Unknown/ambiguous slugs (`paypal`, `virement_emis` outside `Mouvement`, ...) get no or a best-effort category and `needsReview = true`. Account codes `CC`/`LA`/`LJ` → Compte courant / Livret A / Livret Jeune (found by name or created, institution CIC); override with `--accounts <file.json>` and `--categories <file.json>`.
- **Dedupe**: same hashes as bank imports (`computeDedupeHashes`, `classifyRows`), so a re-run inserts nothing. Probable duplicates of rows from another source (CIC CSV) are conflicts: counted and **not inserted** unless `--include-conflicts` (then flagged for review). One `imports` row (`source = 'spreadsheet'`) per account that received rows.
- **Rules**: merchants seen ≥ 3 times and ≥ 90 % in one category and kind get a proposed `contains` rule on their merchant key (skipped when an existing rule already covers them or the pattern would also catch rows filed differently); created at the end of the rule order only with `--create-rules`.

### Categorization

- Categories are assigned by **ordered rules** first (first matching rule wins).
- Uncategorized or flagged transactions go to a **review queue**.
- Correcting a category can create a new rule, so similar transactions are categorized automatically next time.

### Privacy

- **No real financial data** in the repo, tests, fixtures, issues, PRs or logs. Use only anonymized or synthetic fixtures (fake labels, amounts and account numbers).
- Real bank exports live in the git-ignored `data/` folder at the repo root. Never commit it and never paste its contents anywhere.
- Do not log transaction labels, amounts or balances. Query strings carry the transactions search text (`?q=`) and filters: the API request log keeps the path only (`req.url` without its query, no `query`, `Referer` without its query; `req` serializer in `config/logger.ts`, `common/logging/safe-url.ts`, #181), and so does the `path` of `AllExceptionsFilter` log lines (its error body keeps the URL). Failed database queries carry their bound values (Drizzle's `Failed query: ... params: ...` message, `params`, the Postgres `detail`): the logger's `err` serializer and `logMethod` hook (`apps/api/src/common/logging/safe-error.ts`, wired in `config/logger.ts`) reduce them to the error class, SQL text, Postgres code and object names, and stack frames. Keep them when changing the logger.
- **No third-party analytics or tracking**, on the API or on the web app.
- **CSV exports** (the month report, any future one) are written with `apps/web/src/lib/csv.ts`: `text()` cells starting with `=`, `+`, `-`, `@`, a tab or a carriage return are prefixed with `'` and quoted (CSV / formula injection, #175), `amount()` cells are integer cents written with a decimal comma and keep their minus sign.

## Typed API client (codegen pipeline)

The web app talks to the API through a **generated, type-safe client** — do not hand-write fetch calls or edit the generated output.

1. `apps/api` generates `apps/api/openapi.json` via `pnpm --filter @finances/api generate` (`src/generate-spec.ts` boots the Nest app in-memory and dumps the Swagger document), built by `createOpenApiDocument` in `src/config/swagger.ts`). The live Swagger UI (`/api/docs`) and document (`/api/docs-json`) are served **outside production only** (`setupSwagger`, #180): production answers 404, and nothing needs them at runtime.
2. `apps/web` consumes that spec via `@hey-api/openapi-ts` (`apps/web/openapi-ts.config.ts`), emitting a typed fetch client into `apps/web/src/api/` (`client.gen.ts`, `sdk.gen.ts`, `types.gen.ts`).
3. Turborepo's `generate` task chains these, so `pnpm generate` from the root runs API spec generation before web client generation. `build` and `check-types` depend on `generate`.

`apps/web/src/api/` is **generated** — regenerate it (`pnpm generate`) after changing API DTOs/controllers rather than editing it by hand. Annotate API endpoints with `@nestjs/swagger` decorators (`@ApiBody`, `@ApiOkResponse`, `@ApiTags`, etc.) so they surface correctly in the generated client.

## API architecture (NestJS)

Standard NestJS module structure: each domain has a `*.module.ts`, `*.controller.ts`, `*.service.ts` and `*.schema.ts` (Drizzle tables). Base modules: `Auth`, `User`, `Email`, `Database`, `Health`. Finance domains (accounts, imports, transactions, categories, budgets, snapshots, ...) follow the same layout, one module per domain.

**Database**: `DatabaseService` exposes `db` (a Drizzle `PostgresJsDatabase`). All tables extend `coreColumns` from `apps/api/src/database/schema/core.schema.ts`, which adds `id` (UUID PK), `createdAt` and `updatedAt`. Export every schema from `apps/api/src/database/schema/index.ts` and import from there. Money columns are integer cents and transaction dates are `date` columns (see Domain rules).

**Seed data**: `pnpm db:seed` runs `apps/api/src/database/seed.ts`. The default categories (English snake_case `slug`, French display `name`, `kind` = group, hex `color`) live in `apps/api/src/categories/default-categories.ts`; `seedDefaultCategories` inserts the missing slugs with `ON CONFLICT (slug) DO NOTHING`, so it is idempotent and never overwrites a category the user renamed, recoloured or archived; a default category the user deleted is recorded in `deleted_default_categories` and never re-created. Categories are managed from the Catégories page (`/categories`, `CategoriesService`): each has a colour and an icon (#266, `categories.icon`, one of `CATEGORY_ICONS` in `categories/category-icons.ts`, Lucide names mapped in the web's `components/categories/category-icons.tsx`; the default categories get theirs from the seed and migration `0027`), both chosen from its icon on that page; new ones get a slug generated from the name (default slugs stay reserved), archived ones (`archivedAt`) leave the pickers (`pickableCategories`, `apps/web/src/lib/categories.ts`) but keep their history, and deleting one in use moves its transactions, rules, recurring items and budgets (summed) to a category of the same kind in one transaction. Rules and imports should reference categories by `slug`, never by display name. Where `tsx` is not installed (production image), run the compiled script instead: `node dist/database/seed.js` from `apps/api`.

**Auth (single user)**: password auth, plus passkeys (below) — no OAuth. The owner account is created through the normal sign-up form on first launch; as soon as one user exists, `POST /api/auth/register` returns 403 (re-checked under a Postgres advisory lock so concurrent sign-ups can't create a second account) and `GET /api/auth/registration-status` returns `{ open: false }`, which the web app uses to hide sign-up. Email verification (`verify-email`, `resend-verification`) is kept when SMTP is configured; without SMTP (production without `SMTP_HOST`) the owner is created already verified, and an existing unverified owner is marked verified the next time `GET /api/auth/me` loads, since no verification email could ever arrive. Cookie-based JWT (`httpOnly`, `sameSite: lax`, `Secure` in production): the `token` cookie holds a short-lived (15 min) access JWT, and a rotating `refresh_token` cookie (path `/`, 30 days) renews it via `POST /api/auth/refresh`. **Cookie names** (#217, `session-cookies.ts`, `sessionCookieConfig`): in production they are `__Host-token` / `__Host-refresh_token` (no `Domain`, `Path=/`, `Secure`: a sibling subdomain can't toss its own); outside production they keep the plain names, since `Secure` cookies can't be set over HTTP (the phone on `vite dev --host`). Read them only through `readAccessCookie` / `readRefreshCookie` and set or clear them through `setSessionCookies` / `clearSessionCookies`. In production the API reads them under their `__Host-` names only (#226) and every reply that sets or clears the session clears any leftover plain pair. The web server reads either name, `__Host-` first (`ACCESS_COOKIES` / `REFRESH_COOKIES` in `lib/server-session.ts`), and presents a refresh cookie under the name the browser sent; presenting an already-rotated refresh token revokes the whole family (reuse detection). The rotation revokes the presented token with a conditional `UPDATE ... WHERE revoked_at IS NULL RETURNING`, so of two refreshes racing with one token only one wins and the other counts as reuse (#178). A family has an **absolute lifetime** of 90 days from its password or passkey sign-in (`refresh_tokens.authenticated_at`, else its first token; `SESSION_MAX_LIFETIME_MS`): after that the refresh answers 401 and revokes the family, and no renewed token expires later than that end. **The browser never calls the API origin directly**: the web server proxies `/api/*` to the API (see Web architecture), so both cookies are first-party to the web origin. `refresh_token` is scoped to `/` (not `/api/auth`) so page requests carry it to the web SSR guard, which renews an expired access token server-side; the API also clears any leftover cookie at the old `/api/auth` path whenever it sets or clears the session. Passwords are hashed with `bcryptjs`. **New passwords** (sign-up, reset, change: `NewPasswordField` in `auth/dto/fields.ts`, `newPasswordField` in the web's `auth.schemas.ts`) need at least 12 characters and at most 72 bytes (bcrypt ignores the rest); sign-in and "current password" accept any stored password. Forms that take a password (sign-in, sign-up, forgotten password, reset, change, `ReauthSheet`) are `method="post"` and keep their submit button disabled until hydration (`useHydrated`, `lib/use-hydrated.ts`, #203): server-rendered, they would otherwise be submitted natively as a GET with the password in the URL; `e2e/no-js-forms.spec.ts` submits them with JavaScript off. An unknown email still runs one bcrypt comparison against a dummy hash, so a failed sign-in takes as long either way. Password reset goes through `forgot-password` / `reset-password` (tokens handled in `apps/api/src/email/tokens.ts`): only the latest link works (a new one spends the pending ones) and only once, and a reset **ends every session** (all refresh-token families). `POST /api/auth/change-password` (#177, session only, fresh session + current password, throttled like the login; `ChangePasswordCard` on the profile) ends every **other** family and keeps the one whose `refresh_token` made the change. Both take `revokeAccessTokens` to revoke the personal access tokens too. Access JWTs already issued stay valid until they expire (15 minutes). **Sessions** (#217, `auth/sessions/`, ASVS 3.3.4): `GET /api/auth/sessions` lists the active refresh-token families (sign-in method `password` / `passkey` / `sign_up`, sign-in time, last renewal, expiry, a coarse device such as « Safari · iPhone » from `describeDevice`, the current one first; `refresh_tokens.sign_in_method` and `device` are set at sign-in and copied on rotation, never the raw User-Agent, and never a token or hash in the response) and `DELETE /api/auth/sessions/:id` (fresh session) revokes a family, so that device is signed out at its next refresh; both session-only. The web shows them in `SessionsCard` on the profile (« Déconnecter » on the other devices, `ReauthSheet` when the session is not fresh). **Cross-origin writes are refused** (#179, `common/http/same-origin.ts`, a Fastify `onRequest` hook registered in `main.ts`): `SameSite=Lax` still sends the cookies with a form post from a sibling subdomain, so a `POST`/`PUT`/`PATCH`/`DELETE` without `Authorization: Bearer` gets 403 (`Cross-origin request refused`) unless its `Origin` is the app origin (`APP_URL` or `WEBAUTHN_ORIGIN`) or its `Sec-Fetch-Site` is `same-origin` / `none`; without `Sec-Fetch-Site`, a foreign `Origin` is refused. Requests with neither header (the web server's SSR and server-function calls, scripts) pass: never forward a browser's `Origin` from server-side code, and keep the `/api` proxy forwarding both headers unchanged. Use `@UseGuards(JwtGuard)` on every non-public route — `JwtGuard` verifies the cookie (or a personal access token, below) and attaches `{ sub: userId }` to `request.user`; read it with the `@CurrentUser()` decorator (`apps/api/src/auth/decorators/`).

**Passkeys (WebAuthn)** (`apps/api/src/auth/passkeys/`, `@simplewebauthn/server` + `@simplewebauthn/browser`, web side in `lib/passkeys.ts`): discoverable credentials with user verification required, so sign-in needs no email. `POST /api/auth/passkeys/authentication/{options,verify}` are public and issue **the same session as a password login** (`createSession`, `setSessionCookies` in `auth/session-cookies.ts`: same cookies, rotation and reuse detection). Challenges live in `webauthn_challenges`: single use (deleted by the response that answers them, whatever the outcome), 5 minutes, purpose-bound (a registration challenge never signs in). `webauthn_credentials` keeps the credential id, public key (base64url), counter, transports, device type / backed up, an editable name and the last use; the API never returns or logs the credential id, public key or challenge, and library errors become fixed messages. The relying party is `WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGIN`, defaulting to `APP_URL`'s host name and origin (`env.webauthn`; the API refuses to boot when the RP id doesn't cover the origin). Listing, adding (`registration/{options,verify}`), renaming and revoking (delete) are session-only (`@TokenAccess('none')` on the controller). **Fresh session** (#176): adding or revoking a passkey, creating a personal access token and deleting the account (`DELETE /api/profile`) need a recent sign-in: the access JWT carries `auth_time` (last password or passkey sign-in, kept across refreshes in `refresh_tokens.authenticated_at`, read by `JwtGuard` into `request.user.authTime`) and must be under 5 minutes old (`FRESH_AUTH_MAX_AGE_SECONDS`), else 403 `Recent authentication required` (`FreshAuthGuard` / `assertFreshSession` in `auth/guards/fresh-auth.guard.ts`, after `JwtGuard`; put it on any new route that hands over or destroys the account). The web spots that 403 with `needsReauth` (`lib/reauth.ts`) and opens `ReauthSheet` (`components/auth/`), which asks for the password (`POST /api/auth/login`) or a passkey, then runs the action on a second button press (Safari needs a user gesture to create a passkey; a deletion stays an explicit choice). Throttles: options 10/min, verify 5/min per IP (`passkeyOptions`, `passkeyVerify`). On `/auth` the email field has `autocomplete="username webauthn"` and a background conditional-UI ceremony (cancelled on unmount), plus a "Se connecter avec une passkey" button; after a password sign-in, `PasskeyOffer` offers to add one when the account has none and the device has a platform authenticator ("Plus tard" snoozes it 30 days in `localStorage`). The password always stays: there is no passwordless account. Specs drive the real verification with a software authenticator (`passkeys/testing/soft-authenticator.ts`).

**Personal access tokens** (`apps/api/src/auth/access-tokens/`, for the MCP server and scripts): created, listed and revoked from the profile page (`/api/access-tokens`, session only), shown once, stored as a SHA-256 hash (`fin_pat_` + 43 base64url chars), scope `read` or `write`, optional expiry, last-use date, at most 20 active. `JwtGuard` accepts them as `Authorization: Bearer`; when that header is present the cookie is ignored. **Tokens are read-only and deny-by-default for writes**: GET/HEAD routes need `read`; any other method is refused to tokens unless the route declares `@TokenAccess('write')` (or `@TokenAccess('read')` for a POST that saves nothing, e.g. previews); `@TokenAccess('none')` locks a route to the session. Never put `@TokenAccess('write')` on deletes, account or auth changes, or imports other than the bank CSV preview and commit (#103); the routes open to tokens are the `TOKEN_MUTATING_ROUTES` allow-list of `app.routes.spec.ts`, which also names the ones the MCP write tools use (#77: manual transactions, `PATCH /transactions/:id` and `bulk-update`, rule create / preview / apply, `PUT /budgets/:categoryId`; #103: `POST /imports/preview` and `/imports/:id/commit`; #104: snapshots bulk, `POST|PUT /accounts/:id/holdings[/:holdingId]` for manual lines of manual-source crypto accounts only). Every token call is audited (`access_token_audit`: method, route pattern, status — never the URL, query, body, amounts or labels; kept 90 days) and token requests get their own rate-limit bucket keyed by the token hash (`access-token` throttler) on top of the per-IP one. HTTP specs that build `JwtGuard` use `JWT_GUARD_TEST_PROVIDERS` (`auth/guards/jwt-guard.testing.ts`).

**Remote MCP OAuth** (#78, [ADR 0003](docs/adr/0003-remote-mcp-oauth.md), runbook [`docs/runbooks/remote-mcp.md`](docs/runbooks/remote-mcp.md); **shipped disabled, enabling waits for #102**): an OAuth 2.1 authorization server in the API (`apps/api/src/auth/oauth/`) for the claude.ai / Claude app connectors, which reach the app only through the MCP adapter (`apps/mcp --http`). `REMOTE_MCP_ENABLED` (default off) is the kill switch: off, `RemoteMcpModule.register(false)` mounts no `/api/oauth` route and `OAuthService.authenticate` refuses every OAuth token; `REMOTE_MCP_PUBLIC_URL` is the adapter's public origin (issuer; the resource is `<origin>/mcp`), the consent page is `${APP_URL}/oauth/authorize` (web, tailnet, `routes/oauth.authorize.tsx`), `REMOTE_MCP_REDIRECT_URIS` the allow-list (default: the claude.ai and claude.com callbacks). Public RFC routes (`metadata`, DCR `register` for public clients only, `token`, `revoke`; RFC error bodies, throttled `oauthRegister` / `oauthToken`), owner routes session-only (`authorize` GET / POST / `deny`, `grants`, `audit`; approving needs a fresh session), `token-info` for the adapter (OAuth access tokens only). Code + PKCE S256 only, single-use 2-minute codes (a replayed code revokes its grant), access tokens 15 min, refresh tokens rotated with reuse detection (10 s grace for racing refreshes), grants at most 90 days, `resource` checked (RFC 8707). Tokens are `fin_oat_` / `fin_ort_` / `fin_oac_` (SHA-256 stored, never logged); scopes are the token scopes, and `JwtGuard` applies the same `@TokenAccess` rules to OAuth tokens as to personal access tokens (`request.accessToken.kind = 'oauth'`, `id` = the grant). Calls are audited in `oauth_audit` (`OAuthAuditHook`, same fields and retention as `access_token_audit`). The web lists and disconnects grants in `ConnectedAppsCard` (hidden when the API answers 404); `/auth?redirect=` returns only to the consent page (`lib/post-login.ts`). `app.routes.spec.ts` runs with it off; `auth/oauth/remote-mcp.module.spec.ts` audits these routes. The OpenAPI generator turns it on (`generate-spec-env.ts`) and runs under `tsx` without decorator metadata: declare query parameters with `@ApiQuery` and inject with explicit `@Inject(...)` where a constructor mixes tokens.

**Email**: `EmailModule` renders React Email templates (`apps/api/src/email/templates/*.tsx`) to HTML with `@react-email/render` (not the `react-email` CLI, whose preview server is never used) and sends them with `nodemailer` over SMTP (used for password reset). In dev, SMTP points at **Mailpit** (`localhost:1025`, web UI at `localhost:8025`) started by `docker compose`.

**Request bodies**: the global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`) validates every DTO; JSON bodies nested deeper than 32 levels are refused with 400 before it runs (`common/http/json-depth.ts`, a Fastify `preValidation` hook, #182), since the pipe walks bodies recursively.

**Health**: `HealthModule` exposes `GET /api/health` (Terminus), checking the database and, when SMTP is configured, SMTP. The production healthchecks and the deploy script rely on it.

**Path alias**: `#/*` resolves to `./src/*` in both the API and web apps.

## Web architecture (TanStack Start)

File-based routing via TanStack Router — routes live in `apps/web/src/routes/`. `routeTree.gen.ts` is auto-generated; never edit it manually. The root layout is `routes/__root.tsx`.

**UI components**: live in the shared `@finances/ui` package (`packages/ui/src/components/`), Radix UI primitives styled with Tailwind CSS v4. Import them from `@finances/ui`. Use the `cn()` helper (`@finances/ui/lib/utils`, clsx + tailwind-merge) for class merging. App-specific composite components stay under `apps/web/src/components/`.

**Auth state**: client auth context in `apps/web/src/lib/auth-context.tsx`; theme via `apps/web/src/lib/use-theme.ts`.

**API access (same-origin proxy)**: the server route `routes/api/$.ts` (`lib/api-proxy.ts`) forwards every `/api/*` request to `API_URL` (runtime env, default `http://localhost:4000`; `http://api:4000` in the production compose), in dev and in production alike. In the browser the generated client uses a relative base URL (`/api/...` on the web origin, `lib/api-client.ts`); server-side code (SSR, server functions) calls `API_URL` directly (`serverApiUrl()` / `withServerCookies()` in `lib/server-api.ts`). Don't point the browser at the API origin: the session cookies must stay on the web origin for the SSR guard to see them. The proxy reads request bodies only up to the API's own limits and answers 413 itself past them (multipart uploads 5 MB + framing, every other body 1 MiB like the API's Fastify `bodyLimit`, #173, #201): the API closes the connection on an oversized upload, which `fetch` would report as a 502. It drops hop-by-hop headers and `Expect` (undici refuses it).

**Client IP (trusted proxies)**: per-IP rate limits and request logs use the real client IP. The proxy rebuilds `X-Forwarded-For` with only the client IP (`lib/client-ip.ts`): the incoming header is believed only when the TCP peer is in `TRUSTED_PROXIES` (Caddy in production), otherwise the socket address is used. The API sets Fastify `trustProxy` from its own `TRUSTED_PROXIES` (`apps/api/src/config/trusted-proxies.ts`), so it believes the header only from `web`. Both default to `loopback,uniquelocal` (localhost in dev; `none` trusts no one). In production `web` trusts Caddy only: `TRUSTED_PROXIES` also accepts host names, resolved through DNS every 30 s (`TrustedProxies`, trusting nobody while a name doesn't resolve), and the compose file sets `caddy` (`WEB_TRUSTED_PROXIES`, #183), so another container on the shared `proxy` network can't choose its client IP; Caddy itself sees the device's Tailscale address (`100.x` or `fd7a:115c:a1e0::…`) only because `proxy` is dual-stack (infra repo, #251: on an IPv4-only network, IPv6 connections arrive from the Docker gateway through `docker-proxy`); `api` trusts the private ranges of the project network, which is only safe because no port of the production stack is published: never publish the API port. A client sending its own `X-Forwarded-For` can't leave its rate-limit bucket (`trust-proxy.spec.ts`, `client-ip.test.ts`). SSR calls made by the web server itself (loaders, the deduplicated refresh) carry no client IP and count against the web server's address.

**SSR session renewal**: `getMe` (`lib/auth.ts`) resolves the user with `resolveServerSession` (`lib/server-session.ts`): with a valid `token` it just calls `/api/auth/me`; when the access token is missing/expired and a `refresh_token` is present it calls `POST /api/auth/refresh` server-side, appends the rotated `Set-Cookie` headers to the page response, and makes later loaders in the same request use the new cookies. Refreshes are deduplicated per refresh token inside the web process (in-flight calls share one rotation, and a successful one is replayed for 10 s), and the proxied `POST /api/auth/refresh` goes through the same path, so concurrent reloads/tabs or a client refresh racing a reload never trip the API's reuse detection. This assumes a single web instance; the API's rotation and reuse detection are unchanged.

**Authenticated layout**: every signed-in page lives under the pathless layout route `routes/_app.tsx` (files in `routes/_app/`). Its `beforeLoad` guard (`requireUser` in `apps/web/src/lib/auth-guard.ts`) redirects anonymous visitors to `/auth` during SSR, before any protected markup renders (after trying to renew an expired access token, see SSR session renewal), and exposes `user` through the route context. The shell (`apps/web/src/components/app-shell/`) is the `@finances/ui` sidebar (a sheet below `md`, opened from a top bar); add a section by creating `routes/_app/<name>.tsx` and an entry in `app-shell/nav-items.ts` (`NAV_ITEMS`). Settings pages (Profil, Catégories, Règles) are not in that list (#261): they live under the pathless `routes/_app/_settings.tsx` (files in `routes/_app/_settings/`, URLs unchanged), which puts the `SettingsTabs` above them (`NavTabs` from `@finances/ui`: underlined link tabs filling the width in equal shares), and are listed in `SETTINGS_TABS`; the sidebar has one « Réglages » entry (`SETTINGS_ITEM`, opening the first tab and highlighted on all of them) at the bottom, above the account menu, which holds only the theme and sign-out. Every page uses the same full-width layout (`@container space-y-6` under `PageHeader`), never a narrower centred column. `/` only redirects (dashboard or login); there is no public landing page.

**Styling**: Tailwind CSS v4 via `@tailwindcss/vite`. Global styles in `apps/web/src/globals.css`; shared design tokens come from `@finances/ui/globals.css`. Theme (light/dark/auto) is initialized via an inline script in `__root.tsx` before hydration to avoid a flash.

**Mobile**: the app is mainly used from the phone — design mobile-first. It is installable as a PWA (see below); `viewport-fit=cover` is set, and `body` is padded with `env(safe-area-inset-*)` in `globals.css`.

**Mobile layout conventions** (remember the 22px root: `rem` is ~1.4× the usual, while media-query breakpoints stay in 16px units, so `md` is still 768px):

- **Touch targets ≥ 44×44 px.** The `touch-hitbox` utility (`@finances/ui/globals.css`) grows a small, positioned control's hit area with an invisible `::after`; `Button`, `Toggle`, `AlertAction` and chart data `summary`s use it on `pointer: coarse`, `Checkbox`/`Switch`/`RadioGroupItem` always; dropdown items and `size="sm"` native selects are 44px high on touch screens. Keep adjacent targets far enough apart that their hit areas don't overlap (e.g. `min-h-11` rows for radios).
- **No horizontal page scroll down to 320px.** Amounts never break inside (`whitespace-nowrap`); in list rows the amounts go under the label when both don't fit (`flex-wrap`, label `min-w-[7rem] flex-1`, amounts `ml-auto`). Button labels wrap rather than overflow. KPI tiles size their value on the tile (`@container` + `cqi`); they stack one per row on phones (`grid-cols-1 @lg:grid-cols-2 @2xl:grid-cols-4`) and `StatCard` puts its sparkline beside the figures when the tile is at least 260px wide, so a tile stays wider than tall; its value never wraps and is sized on its own column and on the length of the text (#211). Genuinely tabular data scrolls inside its card: `Table` shows a fade on the clipped edge and becomes focusable.
- **Page header** (#246): every page opens with `PageHeader` (`app-shell/PageHeader.tsx`). Its title stays on one line on phones (`text-xl`, `md:text-2xl`; « Prévision fin de mois » is the longest that fits at 320px, so keep titles that short) and its description goes below it, smaller. Page actions are `actions` (`PageAction`: label, icon, `onSelect`, `primary`): buttons beside the title from `md` up; on phones they move into the top bar (`AppTopBar`, through a portal into its slot, `page-actions.tsx`) as an icon button named by its label, or a « Plus d’actions » menu when there are several. Never put a button next to the title by hand. Actions tied to one section (the month navigator, a card, a sticky bottom bar) stay in it. The dashboard has no page action: the accounts not updated, the navigation and the month review lead to the import.
- **Cards in a row keep their own height.** Page grids that put different cards side by side use `items-start` (or stack short cards in one column), so no card is stretched to its neighbour's height with an empty area below its content; only KPI tiles share a row height (#210).
- **Account lists** (#267): Épargne, the dashboard and Comptes draw their accounts with `AccountList` / `AccountListRow` (`components/accounts/AccountList.tsx`, on `ItemList` from `@finances/ui`): no rules, one target per row (account page, or a cash account's transactions on the dashboard) with its chevron last, a 32px type badge (`ACCOUNT_TYPE_ICONS`), left « institution · au 31 oct. » (the type only when neither the group nor the name says it), right the gain over contributions or « à mettre à jour ». No edit button in a list: a value is updated on the account page (« Mettre à jour la valeur », primary for hand-valued accounts), the month close and `StaleValuesReminder`; the dashboard review's accounts to update open that page. The add buttons are stacked at full width, one primary per page (`primaryAction`).
- **One-hand use.** Primary actions sit in sticky bottom bars (`bottom-[calc(1rem+env(safe-area-inset-bottom))]`), kept to one sideways-scrolling row on short screens with the `short-screen:` variant (≤ 600px tall, `apps/web/src/globals.css`); editors open as bottom sheets on phones. Toasts stay clickable over an open sheet and clicking one does not close it (`Toaster` / `SheetContent` in `@finances/ui`), so an « Annuler » for an edit made inside a sheet works (#249). The top bar is `h-12` and shown below `md` only (it opens the navigation sheet): sticky headers under it use `top-(--app-top-bar,3rem)`. From `md` up the sidebar is always on screen; tapping its header (« Finances » and a chevron, or the logo once folded) or Cmd/Ctrl+B folds it down to its icons (page names as tooltips) and back, remembered in the `sidebar_state` cookie read during SSR.
- **Safe areas and keyboard.** `Sheet` pads its edge-to-edge sides with `env(safe-area-inset-*)`, the fixed sidebar (≥ md, e.g. a phone in landscape) is offset from the notch, toasts are offset too. Bottom sheets follow the on-screen keyboard through `--keyboard-inset` (visual viewport, iOS) and `interactive-widget=resizes-content` (Android); size them with `max-h-[calc(90svh-var(--keyboard-inset,0px))]`. Since iOS 26 the form accessory bar (⌃ ⌄ ✓) floats over the page outside that inset: while the keyboard is open the sheet gets `data-keyboard-open`, keeps `--keyboard-accessory` free at its end (84px in a Safari tab, 50px in the installed app, which has no address pill) and, whenever the keyboard opens or changes height, scrolls the element that scrolls the focused field (the sheet, or a body inside it above a sticky footer) so the field stays in view and its end as far as it allows (`packages/ui/src/components/sheet-keyboard.ts`, #205); keep a sheet's actions at the end of its content or in a footer outside its scrolling body.
- **Empty states** (#214): every empty page, card or chart area uses `EmptyState` (`@finances/ui`, `page` or `inline`): an icon, one short line, why, and the action that fixes it (import, add an account, set a target, « Voir septembre 2026 » from an empty month through `NearestMonthButton` / `nearestMonthWithData` in `components/month/`). No block of 0,00 € tiles or empty chart frame without a word: hide them. Abonnements runs the recurring detection by itself once when it has nothing to show (as do bank imports and, with `--commit`, the history import).
- **Audit.** `apps/web/e2e/mobile-layout.spec.ts` (run with `playwright.mobile.config.ts`, never in CI) visits every page at 320/375/390/412/414px and 844×390 in light and dark, and fails on horizontal scroll, hit areas < 44px, form fonts < 16px and text sticking out of its box. It needs a running stack on a throwaway database with data and the owner's credentials in `MOBILE_AUDIT_EMAIL`/`MOBILE_AUDIT_PASSWORD`; the API's global rate limit (60 requests/min per IP) throttles a full run, so run it a page or project at a time (`-g`, `--project`) or against a throwaway API instance whose limit is raised.

### PWA

- **Manifest** `apps/web/public/manifest.json` (`start_url: /dashboard`, shortcuts to Tableau de bord / Opérations / À revoir / Import), linked from `__root.tsx` with the iOS meta tags and light/dark `theme-color` (light `--background` `#f4f7fc`, dark `#090c1a`; update them, the manifest and `offline.html` together if the theme changes).
- **Icons** (`public/icons/*.png`, `public/favicon.ico`) are generated from `public/logo.svg` by `pnpm --filter @finances/web icons` (`apps/web/scripts/generate-icons.mjs`, `sharp`) and committed; re-run it when the logo changes.
- **Service worker**: a small hand-written worker (`src/sw/worker/service-worker.ts`, decisions in `src/sw/routing.ts`, unit tested), bundled into `/sw.js` by the Vite plugin `apps/web/plugins/service-worker.ts` in **production client builds only** (not `vite dev`), and registered by `components/pwa/ServiceWorkerUpdates.tsx` only when `import.meta.env.PROD` and on a secure context (HTTPS or localhost). `vite-plugin-pwa` was not used: the plugin only touches the client environment, so the Nitro SSR bundle and the `/api` server route are unaffected.
  - **Cached** (precache, cache-first): the hashed client assets (JS/CSS) of the build and the shell files listed in `src/sw/precache.ts` (`offline.html`, manifest, icons, favicon, logo). The cache is named `finances-shell-<content hash>`; a new build gets a new name and older caches are deleted when it activates.
  - **Never cached**: `/api/*` (not even intercepted), non-GET and cross-origin requests (Google Fonts included), any other same-origin URL, and server-rendered pages: navigations go network-first and fall back to the static `offline.html` ("Hors ligne", no data) only when the network fails. Requests made by the worker carry no cookies. So nothing sensitive is ever in Cache Storage, before or after logout. Keep it that way: do not add runtime caching of pages or API responses.
  - **In-app navigations** are client-side and never reach the worker's offline fallback. Offline, the guard's `fetchCurrentUser` throws instead of returning null (never a redirect to `/auth`): at once, without a request, when `navigator.onLine` is false (iOS holds requests while offline), and after 8 s otherwise (`loadCurrentUser` in `lib/current-user.ts`), and the router's `defaultErrorComponent` (`components/RouteError.tsx`) shows "Hors ligne" with "Réessayer" (`router.invalidate()`) and retries by itself on `online`; any other guard/loader error gets a generic French page. A thin bar (`app-shell/NavigationProgress.tsx`) shows while a navigation is pending, and a generic page skeleton (`components/PagePending.tsx`, `defaultPendingComponent`) replaces the previous page after 1 s.
  - **Updates**: a new worker waits; the app shows a "Nouvelle version disponible" toast and, on "Recharger", the worker skips waiting and open pages reload. Waiting (rather than `skipWaiting` on install) keeps an open old page from lazy-loading chunks that the new deploy no longer serves. Installed apps re-check for updates when brought back to the foreground (at most hourly).
- **HTTP cache policy**: the API sends `Cache-Control: no-store` (+ `Pragma: no-cache`, `Expires: 0`) on every `/api` response (`onSend` hook, `apps/api/src/common/http/no-store.ts`). On the web server, a global request middleware in `apps/web/src/start.ts` applies `lib/cache-policy.ts` to everything the Start handler answers: `/api/*` (proxy) gets the same headers, every page and server function (signed-in pages, `/auth`, `/`, redirects, errors) gets `private, no-store`, so nothing private lands in the HTTP or back/forward cache. Static files are served by Nitro before that handler: `/assets/*` keeps `public, max-age=31536000, immutable`, `sw.js` and `manifest.json` get `no-cache` (Nitro `routeRules` in `vite.config.ts`) so deploys are picked up. Logout answers `Clear-Site-Data: "cache"` only: `"storage"` would unregister the service worker and wipe its non-sensitive shell cache and the theme preference, and the session cookies are already cleared explicitly. `src/start.ts` replaces Start's default request middleware, so it restates the CSRF middleware for server functions: keep it.
- **Security headers** (#174): the same middleware chain (`src/start.ts`) gives every page, redirect and server function (not `/api`, which keeps the API's helmet headers) a Content-Security-Policy and `X-Frame-Options: DENY` (`lib/security-headers.ts`). `script-src` is `'self'` + a per-response nonce + the hashes of the app's inline `<head>` scripts (`lib/inline-scripts.ts`): the nonce goes to TanStack through the request context and `router.options.ssr.nonce` (`lib/csp-nonce.ts`), and the client reads it back from `<meta property="csp-nonce">`. Never add `'unsafe-inline'` or `'unsafe-eval'` to `script-src` (dev only adds `ws:` for HMR): a new inline script goes in `inline-scripts.ts`, and Zod runs jitless (set there) so it never probes `new Function`. `style-src` keeps `'unsafe-inline'` (server-rendered `style` attributes, runtime `<style>` from Radix / toasts) plus Google Fonts; `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `connect-src` / `worker-src 'self'`. The static `offline.html` gets its own hash-only CSP from a Nitro route rule (`plugins/offline-csp.ts`). `e2e/csp.spec.ts` loads pages and fails on any violation. They also get `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin` and a `Permissions-Policy` denying the features the app never uses (camera, microphone, geolocation, payment, USB, ...; `PERMISSIONS_POLICY`), passkeys allowed on `self` only, the clipboard left at its default (#204, `crossOriginHeaders`); the OAuth consent flow (`/oauth/authorize`, `/auth?redirect=` to it: `keepsOpener`) gets no COOP so the Claude app's popup keeps its opener. `offline.html` gets the same three, static files CORP (Nitro route rule `/**`), and the API helmet's COOP / CORP plus its own `Permissions-Policy` (`common/http/permissions-policy.ts`). No `Cross-Origin-Embedder-Policy`: it would block Google Fonts.
- **Testing**: unit tests cover the routing/precache logic. To check the worker itself, `pnpm --filter @finances/web build` and run `node .output/server/index.mjs` against a throwaway database, open `http://localhost:3000` (secure context), then in DevTools > Application inspect the manifest, the service worker and Cache Storage (only `finances-shell-*` with `/assets/*` and shell files), and tick "Offline" to see the offline page.

## MCP server (`apps/mcp`)

Local MCP server for Claude Desktop / Claude Code (official TypeScript SDK, stdio transport, setup in [`apps/mcp/README.md`](apps/mcp/README.md)). Configured with `FINANCES_API_URL` and `FINANCES_API_TOKEN` (a personal access token: `read` for the read tools, `write` for the write tools). Rules:

- **API only**: tools call `/api/*` with `Authorization: Bearer`, never the database or `apps/web` code. Read tools (`GET`, plus the read-only `POST /budgets/suggest`) keep working with a `read` token; write tools get a clear "lecture seule" error with one.
- **Write tools** (#77, `tools/*-writes.ts`: `add_transaction`, `categorize_transactions`, `mark_one_off`, `set_transaction_note`, `create_rule`, `set_budget_targets`): without `confirm: true` they only read and return a preview of exactly what would change (current state of the selection through `GET /transactions?ids=`); with `confirm: true` they re-read and apply only what still differs, so a repeated call changes nothing more (a manual transaction with the same day, amount and account is refused unless `allowDuplicate`), then list what changed with an undo hint. **No delete tools**: undoing a created transaction, rule or new budget line is done in the app. Annotated `readOnlyHint: false`, `destructiveHint: false`.
- **Bank imports** (#103, `tools/import-writes.ts`): `preview_bank_import` uploads a CIC CSV (a local `.csv` path ≤ 5 MB sent as is, or text sent as UTF-8 with a BOM) to `POST /imports/preview` (writes no transaction), `commit_bank_import` commits it only with `confirm: true` (conflicts only with `includeConflicts`; an already committed preview is a no-op) and lists the import's review-queue rows with their ids; `list_imports` reads `GET /imports`. Only `POST /imports/preview` and `/imports/:id/commit` are open to `write` tokens (`@TokenAccess('write')`); discarding or undoing an import stays session-only.
- **Prompt** `revue_du_mois` ("Revue du mois", `src/prompts.ts`): walks through the month-end review with `month_close_status` (`GET /month-close/:month`), `list_imports` and the import tools, `review_queue`, the write tools and `set_budget_targets` for next month; investment values, ticking steps and closing stay in the app.
- **Investment tools** (#104, `tools/investments.ts`, `tools/investment-writes.ts`, prompt `importer_mes_investissements` in `src/investments-prompt.ts`, setup in [`docs/runbooks/investments-from-drive.md`](docs/runbooks/investments-from-drive.md)): Claude reads the owner's statements with its own Google Drive connector and writes only the extracted values; the app has no Google credentials and makes no Google call. `list_investment_accounts` (read), `add_investment_snapshots` (`POST /accounts/:id/snapshots/bulk`, new / replaced / unchanged days and the net-worth effect; contributions ride on the snapshots, so there is no contributions tool), `sync_crypto_holdings` (quantities as exact decimal strings, `src/quantity.ts`; owns only the `manual` lines of one location: `import` / `sync` lines are never touched, missing manual lines are set to 0 through `PUT`, never deleted; `POST|PUT /accounts/:id/holdings[/:holdingId]` are `@TokenAccess('write')` for it, and a token may only touch the `manual` lines of a `manual`-source account: `CryptoService.assertTokenMayWrite` answers 403 for exchange / wallet accounts and import / sync lines; the tool refuses those accounts up front) and `create_investment_account` (read only: `POST /accounts` stays session-only, it says what to create in the app).
- **Types** come from `apps/api/openapi.json` via `@hey-api/openapi-ts` (types only) into the git-ignored `src/api/generated/` (`@finances/mcp#generate` depends on `@finances/api#generate`); the fetch client is `src/api/client.ts`, which maps 401/403/409/429/5xx/unreachable to French messages returned as tool errors.
- **Output**: French text, euros formatted from cents at the edge (`src/format.ts`), calendar dates as `dd/mm/yyyy` without time zone conversion, "today" in Europe/Paris; partial months are stated with `periodNote`. Small input schemas (≤ 10 fields), names rather than ids for accounts and categories (`tools/lookup.ts`); transactions are shown with their id, which the write tools take. Amounts typed by the model are parsed from text into cents (`parseEuros`), never through a float.
- **Privacy**: stdout is the MCP channel (ESLint forbids `console.log`); stderr gets only a tool name and an HTTP status, never arguments, outputs, amounts, labels or the token.
- **Remote transport** (#78, disabled): `node dist/index.js --http` (`src/http/`) serves `POST /mcp` statelessly (one `McpServer` + `StreamableHTTPServerTransport` per request, JSON responses), the protected resource metadata, and relays the OAuth endpoints to the API (form → JSON). Only `fin_oat_` tokens, checked with `GET /api/oauth/token-info` (cached 30 s) and forwarded to the API; 401 with `resource_metadata`; Origin check, per-IP and per-token limits (`RateLimiter`), client IP from `MCP_TRUSTED_PROXIES` only; refuses to start unless `REMOTE_MCP_ENABLED=true`. `ToolContext.remote` makes tools avoid the server's disk (`preview_bank_import` refuses `filePath`). Not in `docker-compose.prod.yml` yet: the enabling change adds the service and the `infra` repo the public Caddy host.
- **Tests**: Vitest with synthetic fixtures through a real MCP client over `InMemoryTransport` and a mocked `fetch` (`src/test/mock-api.ts`); no database.

## Containerisation

```bash
# Dev — starts PostgreSQL + Mailpit (apps run on the host)
docker compose up -d

# Production images built from this checkout, stack run locally under a throwaway
# project name (the dev stack is also called `finances`; never omit -p locally)
FINANCES_VERSION=local docker compose -p finances-local --env-file <env> \
  -f docker-compose.prod.yml -f docker-compose.build.yml up --build -d
```

`docker-compose.yml` exposes PostgreSQL on `localhost:5432` and Mailpit (SMTP `localhost:1025`, UI `localhost:8025`) with credentials matching the defaults in `apps/api/.env.example`.

**Production stack** (`docker-compose.prod.yml`, runbook [`docs/runbooks/production-stack.md`](docs/runbooks/production-stack.md), deploys [`docs/runbooks/deploy.md`](docs/runbooks/deploy.md)):

- Compose project `name: finances`, deployed in `/srv/finances` (owned by the `deploy` user) with the compose file of the deployed tag and a mode-600 `.env`. Every variable is documented in [`.env.production.example`](.env.production.example); required ones use `${VAR:?}` so the stack refuses to start without them.
- Services `db` (`postgres:17-alpine`, volume `db_data`), `api`, `web`, all `restart: unless-stopped` with healthchecks (`web` checks the whole chain through `/api/health`). **No `ports:` on any service**: `web` also joins the external `proxy` network with the alias `finances-web`, which the server's Caddy (`infra` repo) targets as `finances-web:3000`; `api` and `db` stay on the project network. Never publish a port of this stack (the API trusts forwarded client IPs from private addresses, #49).
- Images `ghcr.io/gregoirebdn/finances-{api,web}:${FINANCES_VERSION}` (`vX.Y.Z` or `sha-<shortsha>`). `docker-compose.build.yml` adds `build:` sections (`pull_policy: build`) to build them from the checkout instead.
- Migrations: `docker compose -f docker-compose.prod.yml run --rm api node dist/database/migrate.js` (`apps/api/src/database/migrate.ts`, Drizzle's runtime migrator; the image ships `drizzle/` through the API package's `files`). Seed: `... run --rm api node dist/database/seed.js`. Both are idempotent and run on every deploy.
- **Hardening** (#183, `x-hardening` in the compose file): `api` and `web` run as `node` with `read_only: true` (only a 16 MB `/tmp` tmpfs is writable), `cap_drop: [ALL]`, `no-new-privileges`, `mem_limit` = `memswap_limit` = `APP_MEM_LIMIT` (default `512m`) and `pids_limit: 256`; `db` keeps only `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID` with `no-new-privileges`. Runtime code must never write outside `/tmp`. The API accepts an incoming `X-Request-Id` only when it is a UUID (`genReqId`, `config/logger.ts`), else it mints one.
- The API image sets `NODE_ENV=production` (session cookies `Secure`) and `HOST=0.0.0.0` (Fastify listens on localhost otherwise). SMTP is optional in production: without `SMTP_HOST` no email is sent and `/api/health` leaves SMTP out; when it is configured, an unreachable SMTP server fails the health check (and a deploy).

The browser only talks to the `web` service: it proxies `/api/*` to the `api` service (`API_URL=http://api:4000`, set in the compose file) and calls it directly during SSR. Caddy forwards everything, `/api` included, to `web`; routing `/api` straight to `api` would bypass the web process's refresh deduplication for client-side refreshes.

The Dockerfiles (`apps/api/Dockerfile`, `apps/web/Dockerfile`) use multi-stage builds with the monorepo root as context (`.dockerignore` keeps `data/`, `.env*` and `.claude/` out of it). The API uses `pnpm deploy --prod --legacy`, which copies the package's `files` (`dist`, `drizzle`) and its production dependencies, so anything `dist/` requires at runtime must be in `dependencies`. The web image copies only the Nitro `.output/` directory; a package imported by `@finances/ui` that bundles CommonJS code requiring `react` (e.g. `recharts`) must also be a dependency of `apps/web`, or the SSR bundle keeps a runtime `require('react')` that fails in the image. Nitro bundles the server and traces only its external packages into `.output/server/node_modules`; its built-in list of native / non-bundleable packages would also pull in any of them that merely resolves (vite, esbuild, sharp, playwright, turbo, ...), so `apps/web/plugins/server-trace.ts` (#242) excludes the workspace's tooling (`traceDeps: ['!pkg']`) and fails the build when anything outside `SERVER_RUNTIME_PACKAGES` (today `tslib`) is traced: exclude a new tool there, or add a real runtime external deliberately.

Target deployment (M6): a VPS running the production compose stack, reachable only through Tailscale. The hosting decisions (Compose per app + one server-level Caddy on a shared `proxy` network, server config in a separate `infra` repo, own domain on the tailnet, one Postgres per app, GHCR images, deploys over Tailscale, restic backups) are in [`docs/adr/0001-multi-app-hosting.md`](docs/adr/0001-multi-app-hosting.md).

## Environment setup (API)

Copy `apps/api/.env.example` to `apps/api/.env` and fill in:

- `DATABASE_URL` — PostgreSQL connection string (default targets the dev Docker container)
- `JWT_SECRET` — JWT signing secret; required in production and at least 32 characters (`openssl rand -hex 32`), or the API refuses to boot (#182); outside production an ephemeral one is generated when unset
- `APP_URL` — web app origin (default: `http://localhost:3000`), used in email links and as the CORS origin
- `TRUSTED_PROXIES` — peers allowed to set the client IP through `X-Forwarded-For` (default `loopback,uniquelocal`, see Client IP)
- `WEBAUTHN_RP_ID`, `WEBAUTHN_ORIGIN` — passkeys relying party; empty = `APP_URL`'s host name and origin (see Passkeys)
- `REMOTE_MCP_ENABLED`, `REMOTE_MCP_PUBLIC_URL`, `REMOTE_MCP_REDIRECT_URIS` — remote MCP OAuth (#78), off by default (see Remote MCP OAuth)

The web app reads two runtime variables (see `apps/web/.env.example`), never exposed to the browser: `API_URL`, the API origin as reached from the web server (default `http://localhost:4000`), and `TRUSTED_PROXIES` (see Client IP).

- SMTP config (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`) — defaults target the dev Mailpit container; in production `SMTP_HOST` is optional (unset = no email)
- Crypto prices (`PRICE_API_ENABLED`, `PRICE_API_URL`, `PRICE_CACHE_TTL_SECONDS`) — default to the CoinGecko public API with a 10-minute cache (see Crypto prices)

Never put real credentials or real financial data in `.env.example`.
