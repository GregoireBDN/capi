# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. Read the **Domain rules** and **Workflow conventions** sections before touching any import, transaction or stats code.

## Product vision

**Finances** is a single-user, self-hosted personal finance tracker. The owner imports bank CSV exports and statements; transactions are parsed, deduplicated, normalized and categorized automatically. Dashboards show:

- all accounts and net worth;
- monthly income, expenses and savings;
- budget vs target per category;
- subscriptions and fixed costs (auto-detected recurring transactions);
- savings and investments (PEA, life insurance, employee savings, crypto);
- an end-of-month forecast.

It is prototyped locally first, then deployed on a VPS and used from the phone as a PWA, ideally reachable only through Tailscale. There is exactly one user: no public sign-up, no multi-tenancy, no third-party analytics.

## Domain rules

These rules are non-negotiable. Code, tests and reviews must enforce them.

### Money and dates

- Money is stored as **integer cents** (`bigint` / `integer` columns), never as floats. Currency is **EUR**.
- Parse amounts from strings directly into cents (e.g. `"1 234,56"` → `123456`); never go through `parseFloat`. Convert to a decimal representation only at the display edge (e.g. `Intl.NumberFormat('fr-FR', { style: 'currency', currency: 'EUR' })`).
- Transaction dates are **calendar dates** (`date` columns / `YYYY-MM-DD` strings), not timestamps. Never shift them through a time zone conversion.
- The app time zone is **Europe/Paris**. Anything that depends on "today" or "this month" (month boundaries, forecasts) is computed in Europe/Paris.

### Transactions

- Every transaction has a `kind`: `expense`, `income` or `transfer`.
- Moves between the user's own accounts (e.g. checking → Livret A, checking → PEA) are `transfer` and must **never** count as income or expense in any statistic, budget or forecast.
- **Transfer links** (#296, [ADR 0004](docs/adr/0004-transfer-links-and-contributions.md)): `transactions.counterpart_account_id` names the owner's other account a transfer goes to (amount < 0) or comes from (amount > 0); only on transfers (any change of kind away from `transfer` clears it, the API answers 400 otherwise), never the row's own account (check constraint), `ON DELETE SET NULL`. Set by hand (`PATCH /api/transactions/:id` `counterpartAccountId`; « Vers » / « Depuis » in `TransactionEditor`, shown on the row), by a rule's « Compte de destination » (`categorization_rules.counterpart_account_id`, rules filing transfers only, given to the transfers they file that have none, on import and on `apply`; an earlier link is never overwritten) and by matching (`transactions/transfer-links/`: the two sides of a transfer between two open cash accounts, opposite amounts at most 3 days apart, closest wins, a tie between two accounts links nothing; both sides linked) on the rows an import (bank CSV, history, demo) just inserted, so a link removed by hand stays removed. `GET /transactions?counterpartAccountId=` lists them. A reconciled manual transfer passes its link to the bank row.

### Recurring items (Abonnements)

- `recurring_items` are series found by the detector (`apps/api/src/recurring/detect.ts`, one per account + merchant key + direction; transfers and one-offs never count): `suggested`, `confirmed` (a real recurring item) or `dismissed` (not one, never suggested again). A detection run refreshes the stats only, never the user's columns (`name`, category, fixed-cost flag, cadence override, `notes`, `status`, `ended_on`, `term_months`, `renewal_kept_on`). A series without a charge for `STALE_PERIODS` (1.5) periods is inactive. Abonnements opens with `RecurringKpis` (the owner's « A. Un total, une barre », #314): the monthly total of the confirmed debits still counted, its year and number of charges, then one stacked bar and a legend of the page's own split, Abonnements · Autres charges fixes · Charges variables (`recurringParts`: disjoint, each part's monthly amount its section header's, so they add up to the total; empty parts left out, the card hidden without any); recurring incomes stay in their section, not in the card.
- **Prepaid subscriptions** (#314, `recurring/prepaid.ts`): a plan paid once, upfront, for a term (`recurring_items.term_months`, 2–60, the app offers 12 / 24 / 36). Declared by the owner from an expense (`POST /api/recurring/prepaid`: the item of its account + merchant becomes, or is created as, `confirmed`, no second occurrence needed; « Abonnement prépayé › » in `TransactionEditor`, « Ajouter un abonnement prépayé » on Abonnements, `AddPrepaidSheet` in three steps; the term changed or cleared with `PATCH /api/recurring/:id` `termMonths`; `DELETE /api/recurring/:id` removes a prepaid item, the undo of a declaration that created it; all session only). Its payments are the transactions linked to it (`transactions.prepaid_item_id`, `ON DELETE SET NULL`, cleared when the kind leaves `expense`); detection runs link a later charge of the merchant within `PREPAID_RENEWAL_WINDOW_DAYS` (30) of the renewal, the closest, as its next payment. Its price is the latest payment, monthly cost = payment ÷ term and yearly = payment × 12 ÷ term (integer cents, half to even), renewal (`renewalDate`, also `nextExpectedDate`) = latest payment + term (`addMonths`, clamped to the month length); inactive once the renewal window is over without a charge. The forecast, the expected costs and the upcoming debits expect the renewal, then one every term, never on or after `ended_on` (« Résilier » defaults to the renewal date). The payment counts in its month's spending and budget, but `transaction_lines.is_one_off` is true for it, so averages and budget suggestions leave it out like a one-off; budget lines list it (`prepaid`, « dont 180,00 € prépayés pour 24 mois »). `renewalReminder` is on from `PREPAID_REMINDER_DAYS` (30) before the renewal to the day, unless cancelled or kept (`keepRenewal` stores `renewal_kept_on`): `RenewalReminders` on Abonnements with « Garder » / « Résilier ». Rows show « Prépayé 24 mois », the monthly cost and « payé 180,00 € pour 24 mois »; transaction rows a flag. The MCP `subscriptions` tool shows the term, the monthly equivalent and the renewal date.
- **Cancellation** (« Résilier », #270) is an end date, not a status: `recurring_items.ended_on` is the **first day no charge is expected any more** (past, today or future), on `confirmed` items only (`PATCH /api/recurring/:id` with `endedOn`, `null` reactivates; 400 on other statuses; refused to access tokens: 403, so the MCP never cancels). The DTO carries `endedOn`, `ended` (`endedOn` ≤ today in Europe/Paris) and `chargedAfterEnd` (latest occurrence booked on or after `endedOn`, a cancellation that did not go through; the end date is never cleared automatically). From `ended_on` an item is out of the forecast and the expected costs (`expectedOccurrences` expects nothing on or after it), and once `ended` out of the yearly / fixed-cost / « Abonnements » totals (`summary`, `endedCount`) and the upcoming debits; before it, it counts as usual. The web shows « Résilié · fin le … » in its section until then, then « Abonnements résiliés » (collapsed, opened when one was charged after its end), with « Réactiver » and « Modifier la date » in the editor; « Résilier » (`EndRecurringSheet`: « Aujourd'hui », « Après la prochaine échéance », any date, note) is for debits only, and every change's toast offers « Annuler ».

### Month comparisons

- Statements are imported by hand, so the current month is often empty or partial. Every page that compares months (dashboard, spending, savings, budget) goes through `apps/api/src/coverage/`: `dataUntil` is the latest booked transaction or committed import end (per account, overall = the latest of them), never after today in Europe/Paris; a month is `complete`, `partial` (first `throughDay` days known) or `empty`.
- A partial month is compared **like for like**: the same first days of the previous month and of the averaged months. An empty month is not compared at all. Without a `month` parameter, endpoints show the current month when it has data, else the month the data stops in. Responses carry a `period` (`MonthPeriodDto`) and the web states it with `PeriodNote` (`lib/period.ts`). Every month page (dashboard review, Dépenses, Opérations, Budget, Épargne, Revue du mois) moves between months with the shared `MonthNavigator` (`components/month/`, #213): previous / next, ← / → on a keyboard, the month name opening a picker with the months that have transactions marked and shortcuts to the current month and to the month the data stops in, from `GET /api/coverage` (`dataUntil`, `defaultMonth`, `months`). It is the first row under `PageHeader`, in `MonthToolbar` (#263, the owner's « proposition A »): one bar across the page (`bg-card`, border) holding the navigator, then the page's filters (`filters(layout)`) and actions at the end of the row, and its `PeriodNote` at the bottom (never a `PeriodNote` placed by hand with a negative margin). The bar is the navigator's container: below 672px of width the filters fold behind a « Filtres » button (bottom sheet, with the number of filters set, `activeFilters`) and the actions get a row of their own. A page with neither gets the `PeriodNote` at the end of the navigator's row (below it on phones), and a lone navigator gets no bar at all. The navigator's box (‹ | month | ›, no ⌄, 44px, `PeriodStepper` in `@finances/ui`) fills its row below 672px of bar width (up to « Filtres » or the bar's edge, the label growing between two 44px arrows: no empty space, the owner's choice) and keeps its own width from 672px, with the short label « oct. 2026 » in bars under 420px and the label as wide as the year's widest month so the arrows never move. Opérations (#264) puts its search in the navigator's row (`search` slot: the rest of the row from 672px, a row of its own below the month on phones) and its filters as chips under it (`FilterChip` / `ToggleChip` in `components/transactions/`: « Compte ⌄ » unset, « Compte : Livret A × » set, a popover of options, categories searchable; « Effacer » only when one is on; on phones only the chips that are on, the rest in the « Filtres » sheet), « Toutes les dates » in the navigator's picker (`allDates`), one totals strip Revenus · Dépenses · Net (only Net toned, `chart-delta-*`), then the list in one card (#327: its header the select-all box in the rows' icon column, the count and the sort filling the rest of the row; the days with sticky headings, the card `overflow-clip`, never `overflow-hidden`, which would break them; « Charger plus » at its end; loading, error and empty states inside it); the URL search params are unchanged. The default month stays out of the URL; the sidebar links carry `?month=` between Dépenses, Opérations, Budget, Épargne and Revue du mois.
- The end-of-month forecast (`apps/api/src/forecast/`, `GET /api/forecast`, #215) projects from the day after `knownUntil` (the selected accounts' `dataUntil`, the latest of them), never from today: recurring items (none on or after a cancelled item's `ended_on`) and the day-to-day estimate fall on their own dates, and the day-to-day expenses entered by hand since then (already in the balance) replace the estimate of the elapsed days (`coveredCents`), so nothing counts twice. Data more than `FORECAST_STALE_AFTER_DAYS` (7) days old (or none) makes it `stale`: indicative, `belowThreshold` null (no low-balance alarm), and the page offers « Importer un relevé » / « Ajouter une dépense ».
- The dashboard is read once a month and follows one month (#321): the review's navigator goes up to the current month, and it opens on the current month (owner's choice: plain to read, past months one « ‹ » away; `GET /api/dashboard/review` `defaultMonth`; `?month=` only when it is not the default). The review (`MonthReview`, #262, the owner's direction « A. Tuiles »): the `MonthNavigator` heads the card with « Clôturé » / « À clôturer » (`closedAt`, from `month_closes`; `closed` only means every account is up to date), then the accounts not updated up to the month end (cash: data stops before it and no import committed after it, opening the import; investments: no value on or after it, opening the account page), the net worth at the month end as a tile on its own line (its change only when investments or anything else moved it, otherwise it equals what was saved) then income / expenses / saved (rate) as tiles (`FigureTile`: one figure per line without notes on a phone), the budget as one stacked bar (owner's « Barre empilée »: expenses with a budget, those without one hatched, the budget as a mark, a legend naming both parts only when both exist, what's left) (no per-category gaps: the owner found them unclear, the envelopes of « Budget » show each category against its budget), and one action from the month's state: « Revue et clôture » while it is open, « Préparer le budget du mois suivant » once closed if the next month has none (`nextMonthBudgeted`), else « Revoir le mois », all at the card's full width. The current month (`current`) is read so far: « En cours », its `PeriodNote`, no account to update, the end-of-month forecast (`ForecastRow`, a chevron to `/forecast`) in place of the net-worth tile (today's is in « Comptes »), no action (closing stays for past months). Every amount is shown once and the month named once. The dashboard has one card per row (owner's choice: review, Budget (`MonthEnvelopes`, the envelopes of the month shown, `GET /api/budgets/envelopes?month=`: during the current month each envelope is one button that notes an expense in it: category icon, name, a 40px « + », its bar with the pace mark, spent / target and what's left, owner's « Appuyer = ajouter »; a past month is read only, without pace mark, « + » or « Ajouter une dépense »; « Détail » opens the budget page on that month), Comptes with today's net worth, its change since the last month end (« +x € depuis le 31 oct. », `previousMonthEndCents`, shown on phones too) and its two parts as tiles, Revenus et dépenses), read top to bottom in full-width strips, never two columns inside a card (owner's « Bandeaux »): from `@[36rem]` the review's four figures (income, expenses, saved, net worth at the month end) sit in one row and the budget on one line (target, long bar, what's left), each envelope takes one line (long bar, what's left at its end); the accounts stay one full-width list with the add buttons one per line at full width. Every dashboard card uses `DashboardCardHeader` (title, optional status, at most one « Voir … › » link); today's net worth is only in « Comptes » (« Patrimoine à ce jour », « Évolution » to `/net-worth`, no net-worth chart on the dashboard).

### Month-end review (closing a month)

- The guided "Revue du mois" (`/month-review`, `apps/api/src/month-close/`, `GET|PATCH /api/month-close/:month`) computes its steps from existing data: imports up to date per cash account (the month review's missing accounts, missing days, running-balance gaps from the stored bank rows, manual transactions excluded), the month's review queue, recurring items (no `suggested` left; the month's price changes and cancelled items charged during the month on or after their end date, `chargedAfterEnd`, ticked as seen), budget and savings (ticked as seen), investment values at the month end, then the close. Only `recurring`, `budget` and `savings` are ticked by hand (`month_closes.acknowledged`).
- `POST /api/month-close/:month/close` (months before the current Europe/Paris month only) freezes the report (flow, net worth at the month end, savings target, totals per category with the month before and targets, largest one-offs, notes) in `month_closes.report` with its shape's version (`report_version`, #369: `REPORT_VERSION` in `month-close/report-version.ts`, the database refusing one without the other); later edits show as `changes` against the live report. A frozen report is read only through `upgradeReport(version, json)`, which turns any stored version into the current DTO one step at a time, filling what an older shape lacks and never recomputing a figure (1 → 2: categories without an icon take their current one, reports before #315 get `plan: null`); a change of what the report holds or means bumps the version and adds one step, so months closed before keep their totals. A closed month refuses ticks and notes until `POST .../reopen`, which drops the frozen report and its version and keeps the notes. Closing is open to write tokens (`@TokenAccess('write')`, #342, the MCP's `close_months`); reopening, ticking steps and notes stay session-only, so undoing a close is done in the app. `GET /api/month-close` lists the closed months, oldest first.

### Accounts

- Account types: `checking`, `savings`, `meal_voucher` (« Titres-restaurant »), `brokerage` (PEA), `life_insurance`, `employee_savings`, `crypto`.
- **Transactional accounts** (checking, savings, meal voucher) have their balance from transactions. **Bank accounts** (checking, savings: `BANK_ACCOUNT_TYPES`, `isBankAccount`) are fed by imports; only they take a bank import, are checked for imports up to date (the month review's accounts to update, the month close's import step) and are projected by the forecast.
- **Meal vouchers** (#298, option 1 of the issue): the employer's card is a `meal_voucher` account whose transactions are all entered by hand (`ManualTransactionSheet`, MCP `add_transaction`): the monthly credit is `income` in the seeded « Titres-restaurant » category (`meal_vouchers`, detected as a recurring credit), each payment an `expense` in its real category (restaurants, groceries), never a transfer, so spending, budgets, the month review and the savings rate count both sides. Its balance is the sum of its transactions, or a balance snapshot plus what is booked after it (the editor's optional « Solde actuel » is stored as the balance at the end of yesterday; « Corriger le solde » on its page). It is in net worth as cash (money the owner holds, spendable on food only), never in the forecast (`GET /api/forecast` refuses it) nor in `coverage/` (manual only). Its page (`MealVoucherAccount.tsx`) leads with « Ajouter un paiement » / « Ajouter un crédit », then the balance and the latest operations; the entry sheet offers it as « Payé avec » for restaurants and groceries and puts the credit on it. Its payments are capped at **25 € a day** (`MEAL_VOUCHER_DAILY_CAP_CENTS`, the legal cap): `POST|PATCH /transactions/manual` answers 400 (`capped at 25 €`) when the card's expenses out of one day, the edited one counted once, would go over it (credits and refunds never are); the sheet shows the day as a gauge (`VoucherDayGauge`: the 25 € bar with the day's card payments from `voucherDayQuery`, the edited one left out, then this one, red when over; « Reste 5 € » or « 13 € max ») on the amount and details steps, and greys out « Ajouter » over it: no error text, no toast. The provider's export and expiry dates are not handled.
- **Investment accounts** (brokerage, life_insurance, employee_savings, crypto) are tracked by **dated value snapshots**. For crypto, the value can also be derived from holdings × price.
- **Archive or delete** (#297): archiving (`PATCH /api/accounts/:id` `archived`) is the default for an account that was used, keeping its history. `DELETE /api/accounts/:id` (session only `@TokenAccess('none')`, fresh session `FreshAuthGuard`; no MCP tool) removes, in one DB transaction, its transactions with their splits, imports, exchange imports (their movements cascade), recurring items, snapshots and savings goal links, then the account, whose other crypto data (holdings, wallet keys and tokens, scans) and account-scoped rules cascade (`imports` and `crypto_imports` restrict the account's deletion, #367). Budgets and categories are untouched; closed months keep their frozen report (their `changes` show the difference). `GET /api/accounts/:id/deletion-preview` counts all of it plus the closed months holding its data. The web: « Archiver ou supprimer » at the end of `AccountEditor` (archive first), then `DeleteAccountScreen` in the same sheet: the counts, « Définitif », the account's name to type (case and spacing ignored), `ReauthSheet` on the fresh-session 403, a toast and back to « Comptes ». No undo.
- A **cash account's page** (#293, `components/accounts/CashAccount.tsx`, one column at every width, owner's choice) answers « where does it stand, is it up to date? »: the header names the institution only, its page actions are « Importer un relevé » (`/import?account=`), « Ajouter une opération » (`ManualTransactionSheet` `initialAccountId`) and « Modifier »; then the balance with « À jour au … · importé il y a … » (a warning when the bank data stops before the previous month end) and the month's money in / out / change (`GET /api/accounts/:id/month-flows`: every movement, transfers included and apart, bank values), the daily balance over 12 months with the statement balances as dots (`GET /api/accounts/:id/balance-history`, `accounts/balance-history.ts`: the anchors of `loadBalances` as of each day, so the last point is the balance; also the window's running-balance gaps, `dataUntil` and the last import day), the latest transactions (`TransactionRow` without selection), the latest imports and gaps, the confirmed recurring debits paid from it, and the statement balances folded at the end. Investment and crypto pages share the header, their actions in `PageHeader` too.
- **Contributions from linked transfers** (#296, `investments/performance.ts` `linkedContributions`): a non-crypto investment account with transfers linked to it gets, at each snapshot, the contributions typed on its last snapshot before the first linked transfer (0 without one) plus the linked transfers booked since, up to that day (`contributionsSource: 'links'`, `linkedTransfersCount`; `typedContributionsCents` when the typed ones since then disagree; `linkedAfterValueCents` for transfers after the latest value, out of the gain). Without links the typed value stays (employee savings paid by the employer). Crypto: an exchange keeps its holdings' cost basis (euros sent to it are only shown); a wallet or manual crypto account gets its **invested base** (#358, below) plus the cost of the exchange withdrawals linked to it after the base's day, or without a base the cost of all of them (a withdrawal of unknown cost is left out and counted, `unknownCostCount`, « dont 2 envois sans coût connu », never hiding the others). The account page lists the linked transfers (`LinkedTransfers`) and charts value vs these contributions (`contributionsHistory`); Épargne puts what was invested beside the result in the header of « Épargne et placements » (`AccountListTotal` `paidInCents`: « résultat +3 975 € » then « investi 30 400 € »), and « Où va mon épargne » (`InvestmentsRecap`, reworked after #344: no totals, no second list of the accounts, each amount shown once) says where the money went: « Sur 12 mois » from `GET /api/investments/flows`, the linked transfers per investment account (two-line rows on phones) and per month, then the movements between accounts, folded.

### Crypto prices

- Crypto accounts hold **holdings** (`crypto_holdings`: asset, location label such as a wallet or exchange, quantity, optional invested cents). Quantities (`numeric(38, 18)`) and EUR prices (`numeric(38, 12)`) are **exact decimal strings** handled with the BigInt helper in `apps/api/src/crypto/decimal.ts`; never `parseFloat` them. Value = round half to even of quantity × price, in cents.
- Prices come from a key-less public API (CoinGecko `simple/price`, behind the `PriceProvider` interface), **server-side only**, all assets batched in one request, cached in `crypto_prices` for `PRICE_CACHE_TTL_SECONDS` (default 600) and kept as last known price when the API fails (flagged stale, never a 500). `PRICE_API_ENABLED=false` disables it: only manual prices (`PUT /api/crypto/prices/:assetId`) are used. The same request carries each price's change over 24 hours (#295, `include_24hr_change`, `PriceProvider.fetchEurQuotes`): `crypto_prices.change_24h_percent` (`numeric(12, 4)`, signed, read from the JSON text with `signedDecimalFromJsonNumber`, an unreadable one left null and never fatal), null for a manual price; shown per asset (`priceChange24hPercent` on valued holdings) and summed into what the portfolio moved.
- **Privacy**: the price API only receives asset ids (and the asset search text), never quantities or values. Never log quantities, prices × quantities or values.
- **Invested base** (#358, extended in #360; `investments/performance.ts` `investedAt`, `takesInvestedBase`, `investments/crypto-flows.ts`): every investment account but an exchange (PEA, life insurance, employee savings, wallet or manual crypto; never an exchange nor a cash account: check constraint `accounts_invested_base_type`, 400) takes what the owner invested up to a day, `accounts.invested_base_cents` / `invested_base_on` (« Investi au … »), never overwritten by a valuation. Its invested amount on a day = the base + what is linked to it after the base's day up to that day (bank transfers for a PEA, the cost of the coins linked to it for crypto: `crypto_movements` withdrawals, `counterpart_account_id`); before the base's day (or without one), what was typed and linked as before (a crypto account: the coins linked so far, else the holdings' invested amounts). From its day the base wins over the amounts typed on a PEA's values, which stay untouched; a crypto account's valuations write it as the snapshot's `contributions_cents` (`CryptoService.accountInvested`), and setting or removing its base rewrites its snapshots from the earlier of the old and new days, so the history and the curve follow; `computePerformance` gives it `contributionsSource: 'base'` (and with a base dated after the latest value, the base as of today). `PUT /api/accounts/:id/invested-base` (`@TokenAccess('write')`), `POST …/invested-base/preview` (`read`, now → with it: invested, result, rate), `DELETE …/invested-base` (session only); `AccountDto` carries `investedBaseCents` / `investedBaseOn`, the performance `investedBase`. A manual account becoming an exchange loses it. The web types it with `InvestedSheet` from the account's summary (below). The MCP: `set_invested_amount`.
- **The summary of every investment account** (#360, the owner's direction « A » with « Barre »; `components/accounts/InvestmentSummary.tsx`, the same on a PEA, a life insurance, employee savings, an exchange, a manual crypto account and a wallet, where it replaced `PerformanceTiles`, `HoldingsPanel`'s tiles and the wallet's own summary): the value once (« Valeur », « Valeur du wallet » with its live holdings), its date and age for a value typed by hand, its change since the previous value (« +415,76 € depuis le 30 sept. »), a wallet's status lines; then « Investi 13 800 € » on a band with the value as one bar, what was put in (grey) and the result (green) or what was lost (red); « Résultat » (euros and rate) and « Sur 1 an » as two tiles abreast (one alone at full width); one line saying where the invested amount comes from (`investedSourceText` in `accounts/invested.ts`: « D’après vos exports, au prix d’achat », « Saisi au 2 janv. 2026 + 3 virements liés », « D’après 14 virements liés », « Saisi sur la valeur du 31 oct. 2026 », « · dont n envois sans coût connu ») with « Modifier » where it is typed (`takesInvestedBase`, not an exchange), and the notes on a typed amount that disagrees with the links or transfers after the latest value. One word for the money put in, « Investi », and one for value − invested, « Résultat » (the owner's choice: « Plus-value » reads wrong when negative), in the tiles, the value editor, the values list, the chart, the lists, the Crypto page, Épargne and the MCP output; never « Versements » nor « plus-value ». An unknown invested amount is never a « — »: one line (« Montant investi pas encore renseigné : le gain ou la perte s’affichera dès qu’il le sera. », or for an exchange that its exports lack the purchase price) and « Renseigner le montant investi ». `InvestedSheet` (a bottom sheet on phones, `STEPPED_SHEET_BOTTOM`) takes it in two steps: « Montant investi » (`AmountField`, « Suivant » greyed out while empty, « Retirer » when there is a base), then « Date » (`SegmentedControl`: the latest value's day as « 31 oct. », « Aujourd’hui », « Autre » with a date field), saved as the invested base with « Annuler » in its toast. A value's own invested amount stays under « Plus d’options » in `SnapshotEditor` (« Investi à cette date », for the statements that print it). Every investment page reads in the same order: summary, what it holds (`HoldingsPanel` and the source card, or `LinkedTransfers`, or « Mouvements »), the evolution chart (value and invested), the values (each with the invested amount that counts, `contributionsHistory`).
- Valuing an account upserts **today's** `balance_snapshot` (Europe/Paris), so balances and net worth use the normal snapshot path; there is no separate crypto net-worth path. A **first** value of 0 € (lines at 0, nothing synced yet) is not recorded: the account stays "not valued yet" (#207).
- A crypto account has a **source** set at creation (`accounts.crypto_source`): `exchange` (with `crypto_provider` binance / coinbase / other; holdings from its imported exports), `wallet` (public keys in `crypto_wallet_keys`: Bitcoin xpub / ypub / zpub, a single Bitcoin address `1…` / `3…` / `bc1q…` / `bc1p…`, or EVM `0x` address, with the chains to read; holdings from the chain) or `manual` (typed by hand; accounts created before sources). A `manual` account holding nothing can become an exchange or a wallet once (`PUT /api/accounts/:id/crypto-source`, session only, #207; « Relier à un wallet ou une plateforme » on its source card, `ChangeCryptoSourceSheet`); its 0 € values are dropped when it never had another one. `GET /api/crypto/settings` says whether prices and wallet sync are on, so the wallet forms warn when sync is off. Esplora is paced at one request per second (`ESPLORA_MIN_INTERVAL_MS`, 1000) and a `Retry-After` ≤ 60 s (none: 10 s) pauses the scan once per sync. `WalletKeyDto.scans` gives each type's used addresses after a complete pass (0 on an xpub: wrong type). ### CIC CSV import format

The first supported bank is CIC. Its CSV export:

- uses `;` as separator;
- is encoded in **Windows-1252** (decode explicitly, do not assume UTF-8);
- uses a comma as decimal separator;
- uses `dd/mm/yyyy` dates;
- has the columns `Date` / `Date de valeur` / `Débit` / `Crédit` / `Libellé` / `Solde`, where `Solde` is the running balance after the row.

The running balance is used to **check continuity** (previous balance + amount = new balance, within a file and across imports) and to rank probable duplicates between sources; it is not part of the dedupe hash.

### Imports

- Imports are **idempotent**: re-importing a file, or a file whose period overlaps a previous import, must not create duplicates.
- Legitimate identical transactions on the same day (same date, amount and label, e.g. two identical card payments) must be **kept**. The dedupe hash includes an occurrence index among identical (date, amount, normalized label) rows in file order, so they stay distinct and a re-imported file still matches. Rows from different sources (e.g. the spreadsheet history vs a CSV export) are compared by a fuzzy probable-duplicate check and shown as conflicts in the preview, never dropped automatically. See `apps/api/src/imports/dedupe/dedupe.ts`.
- Every import goes through a **preview** (new / duplicate / conflicting rows, continuity check) before it is committed. Nothing is written until the user confirms.

### Envelopes and manual transactions

- **Planned income** (#315): a budget line on an **income** category is the month's planned income (salary, benefits, a family transfer…), in the same `budgets` table and with the same rules as expense targets (effective-dated from a month on, carried over to later months without a line of their own, a note, `DELETE` ends it); a transfer category is refused (400) and an income line is never `tracked` (400 when asked). `GET /api/budgets` keeps the expense targets in `items` / `totals` and adds `income` (each line planned vs received from `transaction_lines` with kind `income`, so splits count and transfers or refunds filed in expenses never do; `unplannedCents` outside the plan; `receivedCents` null for an empty month) and `plan` (`toSaveCents` « À épargner » = planned income − budgeted expenses, null without planned income). A partial month is read like for like (`budgets/income.ts`) only where the day is known, from a confirmed recurring credit of the category (monthly, quarterly, yearly): `expectedByNowCents`, `expectedOn`, `status` (`pending`, `received`, `short`, `missing`, `so_far` « reçu à ce jour »). `GET /api/budgets/income-suggestions?month=` prepares a month's income (the plan carried over, else the confirmed recurring credits at their monthly equivalent, rounded to the euro); `history` adds `income` and `plannedIncomeCents` / `receivedIncomeCents` / `plannedSavingsCents` per month. The budget page opens with « Revenus prévus » (`IncomePlanCard`: each line, what came in, the totals, « À épargner »; « Préparer les revenus », `IncomeSuggestionsSheet`), then « Dépenses prévues ». The month close lists the income lines that did not come in (`income.shortfalls`) and freezes `report.plan` (planned vs received income, planned vs actual savings; null in reports frozen before) with the income categories' planned amount as their `targetCents`.
- A budget line can be **tracked** (`budgets.tracked`, "suivre pendant le mois", carried over like the note): the dashboard's « Budget » card (`GET /api/budgets/envelopes?month=`, default the current Europe/Paris month, `current` says which) shows spent / target, what's left and, for the current month, the even-pace mark (target × day / days in the month); a past month's pace is the whole target and nothing is ahead of it, a future month's is 0.
- **Manual transactions** (`POST|PATCH|DELETE /api/transactions/manual`, `ManualTransactionsService`, #137 then #74) are transactions of any kind (expense, income, transfer) with `manual = true`, no import and a random `manual:<uuid>` dedupe hash: positive `amountCents` + `direction` (`out`/`in`, default `in` for income), optional category (without one: review queue, label required), day (never in the future), label, account (open checking / savings / meal voucher; default the oldest open checking), one-off flag, note. They count in statistics and budgets at once, and in account balances from the day after the bank anchor (they never date the balance), but never as imported data: `coverage/` (`dataUntil`) ignores them and the import dedupe (`loadExistingForRange`) leaves them out. The web enters them with `ManualTransactionSheet` (transactions page "Ajouter une opération", dashboard envelopes). The sheet goes in three steps (#245, owner's choice: one decision per screen, « Suivant » / « Retour »): **Catégorie** (kind, a transfer's sign, « Habituels » tiles of usual labels with their category, every category of the kind as wrapping chips; a tap moves on), **Montant**, **Détails** (« Aujourd'hui » / « Hier » / date chips, label, « Payé avec » the bank account or the meal-voucher card for restaurants and groceries, « Plus d'options »: account, sign, one-off, note) then « Ajouter ». An envelope opens at the amount, an edit at the details. Usual labels come from `GET /api/transactions/manual/suggestions?kind=` (labels typed on manual transactions over a year, counted double, and merchants of imported rows seen twice in six months, each with the category filed ≥ 70 % of the time; plus the kind's most used categories over 90 days, the first being the default, #196). On phones (`useIsMobile`) it is a bottom sheet of one height whose amount is typed on its own keypad (`AmountKeypad`, `amount-entry.ts`: exact text, never a float), « Suivant » a key of it: the system keyboard never opens for the amount, and the footer steps aside while the label or note is typed (no button floating above the iOS accessory bar). Elsewhere a dialog: the amount is typed in its field and Enter moves on, then adds. The directions considered and the owner's choice are in #245. Every control is 44px high. Date inputs drop their native look and sheets clip horizontal overflow (`packages/ui` `Input` / `Sheet`), so nothing pans sideways on iOS.
- **Reconciliation** (`apps/api/src/imports/reconcile/`): a `new` import row with the same account and amount, booked at most 5 days from a manual transaction, replaces it on commit (one to one, closest first), keeping its category, kind, note (or typed label), one-off flag and split; the preview shows the match. Unmatched manual transactions of the file's period (up to 5 days before its end) stay and are flagged for review. The commit re-matches against the manual transactions as they are then.

### Hand edits (#74)

- **Imported rows** stay editable for category, kind, flags and note (`PATCH /api/transactions/:id`). Their amount and date change only through "Modifier une opération importée" (`PUT|DELETE /api/transactions/:id/correction`): the bank values are kept in `original_amount_cents` / `original_booking_date` (imported rows only, a check constraint) and read through the generated stored columns `bank_amount_cents` / `bank_booking_date` (#367; `bankAmountCents` / `bankBookingDate` in `transactions.schema.ts`, never written; index `(account_id, bank_booking_date) where not manual`, so bank reads filter `manual = false`) by everything that is bank data (balances, continuity checks, `coverage/`, the dedupe of later imports, month-close gaps), so a re-import never duplicates or overwrites a correction and the dedupe hash never changes. Statistics use the corrected values.
- **Splits** (`transaction_splits`, `PUT|DELETE /api/transactions/:id/splits`): 2–20 parts, each with the transaction's sign, summing exactly to its amount in cents; the transaction keeps the category of its largest part for display. Per-category statistics (spending, budgets and envelopes, planned income, month-close totals, savings flows, the dashboard's monthly flows, the forecast's day-to-day estimate, `GET /transactions/summary`) read the `transaction_lines` view (one line per part, else the transaction), so a split counts in each category. **A part counts with its category's kind** (#357, `splitPartKind` in `transactions/split-kind.ts`; the view reads the category's kind, nothing is stored on the part, since a category's kind can't change while used and a deleted category's parts move to one of the same kind): an incoming part in an expense category is a **refund** of that category (it nets its spending, budget and envelope), an incoming part in an income category is income, an outgoing part in an income category lowers it. A transfer's parts stay transfers, a part in a transfer category keeps the transaction's kind, and a transfer category beside income or expense ones is refused (400). The DTO gives each part its `kind`; « Répartir » (`SplitEditor`) labels a refund part « Remboursement : déduit des dépenses … ». `PUT` is open to write tokens (MCP `split_transaction`), `DELETE` stays session-only. Frozen month-close reports keep their totals; a later split shows in `changes`. A category set for the whole transaction ends its split; a split transaction's amount is locked until the split is removed.
- **Web**: a transactions row (#266, `TransactionRow.tsx`) is the category's icon in its colour (`CategoryAvatar`, a check when selected: tapping it selects the row, a warning dot when to review), one label (`displayLabel`; the raw bank label under it only when it says more, `secondaryLabel`), the category, the account only when there are several open accounts and the list is not filtered to one, small flag icons with an accessible name (ponctuelle, saisie à la main, corrigée, note; « À revoir » is the only text badge) and the amount (`Amount`: income green with « + », expenses in the text colour, internal transfers muted after ⇄; red is kept for what is wrong). Phones stack it on two lines; wide pages (`@xl` container) put the category (`CategoryMenu`: its name as text, opening the categories by kind) and the amount in columns, the account from `@2xl`, with no column headers. On wide pages the category and the amount of manual rows are edited in place. Activating the label opens the row's editor (#280, `TransactionEditor.tsx`; a bottom sheet on phones, a right-hand sheet on wide pages): a settings list, the frequent settings first (Catégorie ›, Note ›, Ponctuelle and À revoir switches saved at once), the rarer ones below (Répartir ›, Corriger montant ou date › for bank rows or Modifier ou supprimer › for manual ones, Type ›); each › opens its own screen with « Retour » (the category as icon chips by kind with a search, the note with « Enregistrer », the split, the correction, the type). The list has no keyboard shortcuts (#265): its controls are reached with Tab and used like any button or select. Every edit shows a toast with "Annuler" (`use-transaction-actions.ts`).

### Spreadsheet history import (one-shot)

The owner's pre-app history (a Google Sheet, ~3,250 categorized rows since 07/2023) is imported once from its CSV exports with `pnpm --filter @finances/api import:history` (code in `apps/api/src/imports/history/`, entry `apps/api/src/database/import-history.ts`; `node dist/database/import-history.js` where `tsx` is missing).

- **Dry run by default**: everything runs in one DB transaction that is rolled back unless `--commit` is passed. It prints counts only; `--report <path>` writes a detailed JSON report (merchant keys, line numbers, conflicts) and refuses any path inside the repo outside `data/`.
- **Inputs**: `Transactions` tab (`Date,Mois,Compte,Libellé,Montant (€),Catégorie,Groupe,Relevé,Ponctuel`, UTF-8, `,`-separated, `-1 234,56 €` amounts) and optionally the `Soldes` tab (`Fin de mois` + one column per account) → `balance_snapshots` on the last day of each month, upserted on (account, date). Columns are matched by name; bad rows are reported, never fatal.
- **Mapping** (`history/mapping.ts`): sheet category slugs → seeded slugs; the kind comes from `Groupe` (`Mouvement` → transfer, `Revenu` → income, `Dépense` → expense) and wins over the category's kind. Unknown/ambiguous slugs (`paypal`, `virement_emis` outside `Mouvement`, ...) get no or a best-effort category and `needsReview = true`. Account codes `CC`/`LA`/`LJ` → Compte courant / Livret A / Livret Jeune (found by name or created, institution CIC); override with `--accounts <file.json>` and `--categories <file.json>`.
- **Dedupe**: same hashes as bank imports (`computeDedupeHashes`, `classifyRows`), so a re-run inserts nothing. Probable duplicates of rows from another source (CIC CSV) are conflicts: counted and **not inserted** unless `--include-conflicts` (then flagged for review). One `imports` row (`source = 'spreadsheet'`) per account that received rows.
- **Rules**: merchants seen ≥ 3 times and ≥ 90 % in one category and kind get a proposed `contains` rule on their merchant key (skipped when an existing rule already covers them or the pattern would also catch rows filed differently); created at the end of the rule order only with `--create-rules`.

### Categorization

- Categories are assigned by **ordered rules** first (first matching rule wins).
- **The order is computed** (#299, `compareRules` in `categories/rules/categorize.ts`): higher `categorization_rules.priority` first (0 by default), then the most specific rule (a regex, then the longer folded pattern, then more account / amount conditions), then the oldest (`position` is the creation order only); the list carries each rule's `rank`. Overlaps are shown, not ordered by hand: `GET /api/categorization-rules/insights` gives each rule's matches over 12 months and the conflicts (two enabled rules matching the same transactions, not filed by hand, with another category or kind), `POST /:id/prefer` (session only) makes a rule win by raising its priority above the other's, and the preview lists the previewed rule's conflicts (MCP `create_rule` shows them). The web (`components/rules/`) reads rules as sentences grouped by category, edits them in three steps (« Quelles opérations ? » with the live matches of `POST /matches`, « Classer dans », « Vérifier » with the preview; « Avancé » holds regex, account, amount, kind, active and priority) and applies the rules after every save, with « Annuler ».
- Uncategorized or flagged transactions go to a **review queue**: « À revoir », a filter of Opérations (#322, `?review=true`; `/review` redirects to it with every date, `REVIEW_SEARCH`). Filtered on it, the list's header counts what is left with « Tout valider » once every loaded row has a category, the totals strip is hidden, each row to review ends with « Valider » (or « Classer » on narrow pages, opening the editor on the categories), and a row validated or filed leaves the list at once (`leaveReview`, then a refetch), « Annuler » bringing it back. Its count is the badge of « Opérations » in the sidebar, itself a link to the filter.
- Correcting a category can create a new rule, so similar transactions are categorized automatically next time.

### Privacy

- **No real financial data** in the repo, tests, fixtures, issues, PRs or logs. Use only anonymized or synthetic fixtures (fake labels, amounts and account numbers).
- Real bank exports live in the git-ignored `data/` folder at the repo root. Never commit it and never paste its contents anywhere.
- Do not log transaction labels, amounts or balances. Query strings carry the transactions search text (`?q=`) and filters: the API request log keeps the path only (`req.url` without its query, no `query`, `Referer` without its query; `req` serializer in `config/logger.ts`, `common/logging/safe-url.ts`, #181), and so does the `path` of `AllExceptionsFilter` log lines (its error body keeps the URL). Failed database queries carry their bound values (Drizzle's `Failed query: ... params: ...` message, `params`, the Postgres `detail`): the logger's `err` serializer and `logMethod` hook (`apps/api/src/common/logging/safe-error.ts`, wired in `config/logger.ts`) reduce them to the error class, SQL text, Postgres code and object names, and stack frames. Keep them when changing the logger.
- **No third-party analytics or tracking**, on the API or on the web app.
- **CSV exports** (the month report, any future one) are written with `apps/web/src/lib/csv.ts`: `text()` cells starting with `=`, `+`, `-`, `@`, a tab or a carriage return are prefixed with `'` and quoted (CSV / formula injection, #175), `amount()` cells are integer cents written with a decimal comma and keep their minus sign.

## Typed API client (codegen pipeline)

The web app talks to the API through a **generated, type-safe client** — do not hand-write fetch calls or edit the generated output.

1. `apps/api` generates `apps/api/openapi.json` via `pnpm --filter @finances/api generate` (`src/generate-spec.ts` boots the Nest app in-memory and dumps the Swagger document), built by `createOpenApiDocument` in `src/config/swagger.ts`). The live Swagger UI (`/api/docs`) and document (`/api/docs-json`) are served **outside production only** (`setupSwagger`, #180): production answers 404, and nothing needs them at runtime.
2. `apps/web` consumes that spec via `@hey-api/openapi-ts` (`apps/web/openapi-ts.config.ts`), emitting a typed fetch client into `apps/web/src/api/` (`client.gen.ts`, `sdk.gen.ts`, `types.gen.ts`).
3. Turborepo's `generate` task chains these, so `pnpm generate` from the root runs API spec generation before web client generation. `build` and `check-types` depend on `generate`.

`apps/web/src/api/` is **generated** — regenerate it (`pnpm generate`) after changing API DTOs/controllers rather than editing it by hand. Annotate API endpoints with `@nestjs/swagger` decorators (`@ApiBody`, `@ApiOkResponse`, `@ApiTags`, etc.) so they surface correctly in the generated client.

## API architecture (NestJS)

Standard NestJS module structure: each domain has a `*.module.ts`, `*.controller.ts`, `*.service.ts` and `*.schema.ts` (Drizzle tables). Base modules: `Auth`, `User`, `Email`, `Database`, `Health`. Finance domains (accounts, imports, transactions, categories, budgets, snapshots, ...) follow the same layout, one module per domain.

**Database**: `DatabaseService` exposes `db` (a Drizzle `PostgresJsDatabase`). All tables extend `coreColumns` from `apps/api/src/database/schema/core.schema.ts`, which adds `id` (UUID PK), `createdAt` and `updatedAt`. **Instants are `timestamptz`** (`timestamp(..., { withTimezone: true })`), never `timestamp` without time zone, and `updated_at` is kept by the database: the `set_updated_at()` trigger (migration `0039`) moves it on every update that does not set it itself, raw SQL included; a migration creating a table adds its `<table>_set_updated_at` trigger (`database/schema/constraints.spec.ts` fails otherwise, and when a `timestamp` without time zone appears). **The database enforces what the services guarantee** (#367, ADR 0005 R3): check constraints on `transactions` (`manual` ⇔ no `import_id` ⇔ `manual:` hash, counterpart only on transfers, prepaid link only on expenses, corrections only on bank rows), `recurring_items` (`ended_on` on confirmed items only, so leaving `confirmed` clears it; a term on debits only), `accounts` (sync times on crypto accounts only), `savings_goals` (typed amount iff manual), `month_closes` (ticks among `recurring`, `budget`, `savings`); one spec each in `constraints.spec.ts`. A write path that changes a row's kind or status clears what the new value forbids. Spec fixtures that insert bank rows by hand give them an import with `bankRows(tx, rows)` (`transactions/testing/bank-rows.ts`). Export every schema from `apps/api/src/database/schema/index.ts` and import from there. Money columns are integer cents and transaction dates are `date` columns (see Domain rules). The model (ER diagrams, each table's invariants, stored vs derived values) is described in [`docs/architecture/data-model.md`](docs/architecture/data-model.md); the consolidation proposed by #362 is [ADR 0005](docs/adr/0005-data-model-consolidation.md).

**Seed data**: `pnpm db:seed` runs `apps/api/src/database/seed.ts`. The default categories (English snake_case `slug`, French display `name`, `kind` = group, hex `color`) live in `apps/api/src/categories/default-categories.ts`; `seedDefaultCategories` inserts the missing slugs with `ON CONFLICT (slug) DO NOTHING`, so it is idempotent and never overwrites a category the user renamed, recoloured or archived; a default category the user deleted is recorded in `deleted_default_categories` and never re-created. Categories are managed from the Catégories page (`/categories`, `CategoriesService`): each has a colour and an icon (#266, `categories.icon`, one of `CATEGORY_ICONS` in `categories/category-icons.ts`, Lucide names mapped once in `@finances/ui` (`components/category-icon.tsx`: `CATEGORY_ICONS`, same keys and order as the API, read by the picker and by `CategoryIcon`, #287); the default categories get theirs from the seed and migration `0027`, and a re-seed gives a default category without an icon its default one, never replacing a chosen one), both chosen from its icon on that page; wherever a category is named the web shows `CategoryIcon` (`icon`, `color`, `size` `sm` in legends and chips / `md` in list rows, `fallback` glyph; the glyph in the colour on a tile at ~14 % of it; on every page since #288, the only way a category is drawn: no colour dot; recurring and forecast items carry `categoryIcon`, the month report's categories `icon`, a report frozen before icons taking the category's current one through `upgradeReport`), chart legends taking it through the series' or slice's `icon`; new ones get a slug generated from the name (default slugs stay reserved), archived ones (`archivedAt`) leave the pickers (`pickableCategories`, `apps/web/src/lib/categories.ts`) but keep their history, and deleting one in use moves its transactions, rules, recurring items and budgets (summed) to a category of the same kind in one transaction. Rules and imports should reference categories by `slug`, never by display name. Where `tsx` is not installed (production image), run the compiled script instead: `node dist/database/seed.js` from `apps/api`.

**Auth (single user)**: password auth, plus passkeys (below) — no OAuth. The owner account is created through the normal sign-up form on first launch; as soon as one user exists, `POST /api/auth/register` returns 403 (re-checked under a Postgres advisory lock so concurrent sign-ups can't create a second account) and `GET /api/auth/registration-status` returns `{ open: false }`, which the web app uses to hide sign-up. Email verification (`verify-email`, `resend-verification`) is kept when SMTP is configured; without SMTP (production without `SMTP_HOST`) the owner is created already verified, and an existing unverified owner is marked verified the next time `GET /api/auth/me` loads, since no verification email could ever arrive. Cookie-based JWT (`httpOnly`, `sameSite: lax`, `Secure` in production): the `token` cookie holds a short-lived (15 min) access JWT, and a rotating `refresh_token` cookie (path `/`, 30 days) renews it via `POST /api/auth/refresh`. **Cookie names** (#217, `session-cookies.ts`, `sessionCookieConfig`): in production they are `__Host-token` / `__Host-refresh_token` (no `Domain`, `Path=/`, `Secure`: a sibling subdomain can't toss its own); outside production they keep the plain names, since `Secure` cookies can't be set over HTTP (the phone on `vite dev --host`). Read them only through `readAccessCookie` / `readRefreshCookie` and set or clear them through `setSessionCookies` / `clearSessionCookies`. In production the API reads them under their `__Host-` names only (#226) and every reply that sets or clears the session clears any leftover plain pair. The web server reads either name, `__Host-` first (`ACCESS_COOKIES` / `REFRESH_COOKIES` in `lib/server-session.ts`), and presents a refresh cookie under the name the browser sent; presenting an already-rotated refresh token revokes the whole family (reuse detection). The rotation revokes the presented token with a conditional `UPDATE ... WHERE revoked_at IS NULL RETURNING`, so of two refreshes racing with one token only one revokes it (#178). **Grace for a lost response** (#292): a token rotated less than `SESSION_REFRESH_REUSE_GRACE_MS` (60 s) ago whose successors (`refresh_tokens.parent_id`) are all unused gets one more successor instead of burning the family (the loser of a race, a response lost to the network, an iOS suspension or a web restart); renewing one of those siblings drops the others (`superseded`), so a later use of a dropped one, or of the old token after the grace or once a successor was used, is still reuse. Revocations keep their reason (`refresh_tokens.revoked_reason`: `rotated`, `superseded`, `reuse`, `lifetime`, `logout`, `signed_out`, `password`); every refused refresh is logged with its reason only (`Session refresh refused: unknown | expired | reuse | lifetime | revoked | no cookie`), every session end with its kind, never a token, id or user. **Only a 401 means signed out** (#292; `GET /api/auth/me` answers 401, never an empty 200, for a token whose user no longer exists: a deleted account or a reset database): on the web, `me` and the refresh answering 429, 5xx or nothing are retried (`Retry-After` honoured, capped) then shown as the error page with « Réessayer » (`SessionUnavailableError`, `lib/session-errors.ts`), never as a redirect to `/auth`: `currentUserFromResult` / `loadCurrentUser` (`lib/current-user.ts`, one retry), the browser refresh (`lib/session-refresh.ts`, 3 tries, a transient failure handed to the caller as its own status, never the 401), and the SSR path (`resolveServerSession` returns `unavailable`, `getMe` forwards the rotated cookies then throws). The guard's signed-in answer is reused for `CURRENT_USER_CACHE_MS` (10 s, in-flight calls shared, dropped on logout and on a refused refresh): the router preloads on intent, and every hovered or touched link ran the `_app` guard's `GET /api/auth/me` against its 60 / min limit. A family has an **absolute lifetime** of 90 days from its password or passkey sign-in (`refresh_tokens.authenticated_at`, else its first token; `SESSION_MAX_LIFETIME_MS`): after that the refresh answers 401 and revokes the family, and no renewed token expires later than that end. **The browser never calls the API origin directly**: the web server proxies `/api/*` to the API (see Web architecture), so both cookies are first-party to the web origin. `refresh_token` is scoped to `/` (not `/api/auth`) so page requests carry it to the web SSR guard, which renews an expired access token server-side; the API also clears any leftover cookie at the old `/api/auth` path whenever it sets or clears the session. Passwords are hashed with `bcryptjs`. **New passwords** (sign-up, reset, change: `NewPasswordField` in `auth/dto/fields.ts`, `newPasswordField` in the web's `auth.schemas.ts`) need at least 12 characters and at most 72 bytes (bcrypt ignores the rest); sign-in and "current password" accept any stored password. Forms that take a password (sign-in, sign-up, forgotten password, reset, change, `ReauthSheet`) are `method="post"` and keep their submit button disabled until hydration (`useHydrated`, `lib/use-hydrated.ts`, #203): server-rendered, they would otherwise be submitted natively as a GET with the password in the URL; `e2e/no-js-forms.spec.ts` submits them with JavaScript off. An unknown email still runs one bcrypt comparison against a dummy hash, so a failed sign-in takes as long either way. Password reset goes through `forgot-password` / `reset-password` (tokens handled in `apps/api/src/email/tokens.ts`): only the latest link works (a new one spends the pending ones) and only once, and a reset **ends every session** (all refresh-token families). `POST /api/auth/change-password` (#177, session only, fresh session + current password, throttled like the login; `ChangePasswordCard` in Réglages › Sécurité) ends every **other** family and keeps the one whose `refresh_token` made the change. Both take `revokeAccessTokens` to revoke the personal access tokens too. Access JWTs already issued stay valid until they expire (15 minutes). **Sessions** (#217, `auth/sessions/`, ASVS 3.3.4): `GET /api/auth/sessions` lists the active refresh-token families (sign-in method `password` / `passkey` / `sign_up`, sign-in time, last renewal, expiry, a coarse device such as « Safari · iPhone » from `describeDevice`, the current one first; then the families burned by reuse detection in the last 30 days, with `reuseDetectedAt`, shown as « Déconnecté : réutilisation détectée » without an action, #292; `refresh_tokens.sign_in_method` and `device` are set at sign-in and copied on rotation, never the raw User-Agent, and never a token or hash in the response) and `DELETE /api/auth/sessions/:id` (fresh session) revokes a family, so that device is signed out at its next refresh; both session-only. The web shows them in `SessionsCard` in Réglages › Sécurité (« Déconnecter » on the other devices, `ReauthSheet` when the session is not fresh). **Cross-origin writes are refused** (#179, `common/http/same-origin.ts`, a Fastify `onRequest` hook registered in `main.ts`): `SameSite=Lax` still sends the cookies with a form post from a sibling subdomain, so a `POST`/`PUT`/`PATCH`/`DELETE` without `Authorization: Bearer` gets 403 (`Cross-origin request refused`) unless its `Origin` is the app origin (`APP_URL` or `WEBAUTHN_ORIGIN`) or its `Sec-Fetch-Site` is `same-origin` / `none`; without `Sec-Fetch-Site`, a foreign `Origin` is refused. Outside production only (#339), an `Origin` equal to the origin the request was addressed to (`X-Forwarded-Proto` + `X-Forwarded-Host` set by the web proxy, else `Host`) also passes: the phone opens the dev server at the Mac's LAN address over plain HTTP, where browsers send no `Sec-Fetch-*` and the `Origin` is not `APP_URL`. Requests with neither header (the web server's SSR and server-function calls, scripts) pass: never forward a browser's `Origin` from server-side code, and keep the `/api` proxy forwarding both headers unchanged. Use `@UseGuards(JwtGuard)` on every non-public route — `JwtGuard` verifies the cookie (or a personal access token, below) and attaches `{ sub: userId }` to `request.user`; read it with the `@CurrentUser()` decorator (`apps/api/src/auth/decorators/`).

**Passkeys (WebAuthn)** (`apps/api/src/auth/passkeys/`, `@simplewebauthn/server` + `@simplewebauthn/browser`, web side in `lib/passkeys.ts`): discoverable credentials with user verification required, so sign-in needs no email. `POST /api/auth/passkeys/authentication/{options,verify}` are public and issue **the same session as a password login** (`createSession`, `setSessionCookies` in `auth/session-cookies.ts`: same cookies, rotation and reuse detection). Challenges live in `webauthn_challenges`: single use (deleted by the response that answers them, whatever the outcome), 5 minutes, purpose-bound (a registration challenge never signs in). `webauthn_credentials` keeps the credential id, public key (base64url), counter, transports, device type / backed up, an editable name and the last use; the API never returns or logs the credential id, public key or challenge, and library errors become fixed messages. The relying party is `WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGIN`, defaulting to `APP_URL`'s host name and origin (`env.webauthn`; the API refuses to boot when the RP id doesn't cover the origin). Listing, adding (`registration/{options,verify}`), renaming and revoking (delete) are session-only (`@TokenAccess('none')` on the controller). **Fresh session** (#176): adding or revoking a passkey, creating a personal access token and deleting the account (`DELETE /api/profile`) need a recent sign-in: the access JWT carries `auth_time` (last password or passkey sign-in, kept across refreshes in `refresh_tokens.authenticated_at`, read by `JwtGuard` into `request.user.authTime`) and must be under 5 minutes old (`FRESH_AUTH_MAX_AGE_SECONDS`), else 403 `Recent authentication required` (`FreshAuthGuard` / `assertFreshSession` in `auth/guards/fresh-auth.guard.ts`, after `JwtGuard`; put it on any new route that hands over or destroys the account). The web spots that 403 with `needsReauth` (`lib/reauth.ts`) and opens `ReauthSheet` (`components/auth/`), which asks for the password (`POST /api/auth/login`) or a passkey, then runs the action on a second button press (Safari needs a user gesture to create a passkey; a deletion stays an explicit choice). Throttles: options 10/min, verify 5/min per IP (`passkeyOptions`, `passkeyVerify`). On `/auth` the email field has `autocomplete="username webauthn"` and a background conditional-UI ceremony (cancelled on unmount), plus a "Se connecter avec une passkey" button; after a password sign-in, `PasskeyOffer` offers to add one when the account has none and the device has a platform authenticator ("Plus tard" snoozes it 30 days in `localStorage`). The password always stays: there is no passwordless account. Specs drive the real verification with a software authenticator (`passkeys/testing/soft-authenticator.ts`).

**Personal access tokens** (`apps/api/src/auth/access-tokens/`, for the MCP server and scripts): created, listed and revoked in Réglages › Claude et accès (`/api/access-tokens`, session only), shown once, stored as a SHA-256 hash (`fin_pat_` + 43 base64url chars), scope `read` or `write`, optional expiry, last-use date, at most 20 active. `JwtGuard` accepts them as `Authorization: Bearer`; when that header is present the cookie is ignored. **Tokens are read-only and deny-by-default for writes**: GET/HEAD routes need `read`; any other method is refused to tokens unless the route declares `@TokenAccess('write')` (or `@TokenAccess('read')` for a POST that saves nothing, e.g. previews); `@TokenAccess('none')` locks a route to the session. Never put `@TokenAccess('write')` on deletes, account or auth changes, or imports other than the bank CSV preview and commit (#103); the routes open to tokens are the `TOKEN_MUTATING_ROUTES` allow-list of `app.routes.spec.ts`, which also names the ones the MCP write tools use (#77: manual transactions, `PATCH /transactions/:id` and `bulk-update`, rule create / preview / apply, `PUT /budgets/:categoryId`; #103: `POST /imports/preview` and `/imports/:id/commit`; #342: `POST /month-close/:month/close`; #358: `PUT /accounts/:id/invested-base` and its read-only preview; #357: `PUT /transactions/:id/splits`; #104: snapshots bulk, `POST|PUT /accounts/:id/holdings[/:holdingId]` for manual lines of manual-source crypto accounts only). Every token call is audited (`access_token_audit`: method, route pattern, status — never the URL, query, body, amounts or labels; kept 90 days) and token requests get their own rate-limit bucket keyed by the token hash (`access-token` throttler) on top of the per-IP one. HTTP specs that build `JwtGuard` use `JWT_GUARD_TEST_PROVIDERS` (`auth/guards/jwt-guard.testing.ts`).

**Remote MCP OAuth** (#78, [ADR 0003](docs/adr/0003-remote-mcp-oauth.md), runbook [`docs/runbooks/remote-mcp.md`](docs/runbooks/remote-mcp.md); **off by default**: the #102 audit passed and #328 ships the adapter's image and production service, turned on by the owner in the server's `.env`): an OAuth 2.1 authorization server in the API (`apps/api/src/auth/oauth/`) for the claude.ai / Claude app connectors, which reach the app only through the MCP adapter (`apps/mcp --http`). `REMOTE_MCP_ENABLED` (default off) is the kill switch: off, `RemoteMcpModule.register(false)` mounts no `/api/oauth` route and `OAuthService.authenticate` refuses every OAuth token; `REMOTE_MCP_PUBLIC_URL` is the adapter's public origin (issuer; the resource is `<origin>/mcp`), the consent page is `${APP_URL}/oauth/authorize` (web, tailnet, `routes/oauth.authorize.tsx`), `REMOTE_MCP_REDIRECT_URIS` the allow-list (default: the claude.ai and claude.com callbacks). Public RFC routes (`metadata`, DCR `register` for public clients only, `token`, `revoke`; RFC error bodies, throttled `oauthRegister` / `oauthToken`), owner routes session-only (`authorize` GET / POST / `deny`, `grants`, `audit`; approving needs a fresh session), `token-info` for the adapter (OAuth access tokens only). Code + PKCE S256 only, single-use 2-minute codes (a replayed code revokes its grant), access tokens 15 min, refresh tokens rotated with reuse detection (10 s grace for racing refreshes), grants at most 90 days, `resource` checked (RFC 8707). Tokens are `fin_oat_` / `fin_ort_` / `fin_oac_` (SHA-256 stored, never logged); scopes are the token scopes, and `JwtGuard` applies the same `@TokenAccess` rules to OAuth tokens as to personal access tokens (`request.accessToken.kind = 'oauth'`, `id` = the grant). Calls are audited in `oauth_audit` (`OAuthAuditHook`, same fields and retention as `access_token_audit`). The web lists grants with the tokens in « Accès actifs » and disconnects them from their detail (Claude et accès, #329; the connector choice is hidden when the API answers 404); `/auth?redirect=` returns only to the consent page (`lib/post-login.ts`). `app.routes.spec.ts` runs with it off; `auth/oauth/remote-mcp.module.spec.ts` audits these routes. The OpenAPI generator turns it on (`generate-spec-env.ts`) and runs under `tsx` without decorator metadata: declare query parameters with `@ApiQuery` and inject with explicit `@Inject(...)` where a constructor mixes tokens.

**Email**: `EmailModule` renders React Email templates (`apps/api/src/email/templates/*.tsx`) to HTML with `@react-email/render` (not the `react-email` CLI, whose preview server is never used) and sends them with `nodemailer` over SMTP (used for password reset). In dev, SMTP points at **Mailpit** (`localhost:1025`, web UI at `localhost:8025`) started by `docker compose`.

**Request bodies**: the global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`) validates every DTO; JSON bodies nested deeper than 32 levels are refused with 400 before it runs (`common/http/json-depth.ts`, a Fastify `preValidation` hook, #182), since the pipe walks bodies recursively.

**Health**: `HealthModule` exposes `GET /api/health` (Terminus), checking the database and, when SMTP is configured, SMTP. The production healthchecks and the deploy script rely on it.

**Path alias**: `#/*` resolves to `./src/*` in both the API and web apps.

## Web architecture (TanStack Start)

File-based routing via TanStack Router — routes live in `apps/web/src/routes/`. `routeTree.gen.ts` is auto-generated; never edit it manually. The root layout is `routes/__root.tsx`.

**UI components**: live in the shared `@finances/ui` package (`packages/ui/src/components/`), Radix UI primitives styled with Tailwind CSS v4. Import them from `@finances/ui`. Use the `cn()` helper (`@finances/ui/lib/utils`, clsx + tailwind-merge) for class merging. App-specific composite components stay under `apps/web/src/components/`.

**Auth state**: client auth context in `apps/web/src/lib/auth-context.tsx`; theme via `apps/web/src/lib/use-theme.ts`.

**API access (same-origin proxy)**: the server route `routes/api/$.ts` (`lib/api-proxy.ts`) forwards every `/api/*` request to `API_URL` (runtime env, default `http://localhost:4000`; `http://api:4000` in the production compose), in dev and in production alike. In the browser the generated client uses a relative base URL (`/api/...` on the web origin, `lib/api-client.ts`); server-side code (SSR, server functions) calls `API_URL` directly (`serverApiUrl()` / `withServerCookies()` in `lib/server-api.ts`). Don't point the browser at the API origin: the session cookies must stay on the web origin for the SSR guard to see them. The proxy reads request bodies only up to the API's own limits and answers 413 itself past them (multipart uploads 5 MB + framing, every other body 1 MiB like the API's Fastify `bodyLimit`, #173, #201): the API closes the connection on an oversized upload, which `fetch` would report as a 502. It drops hop-by-hop headers and `Expect` (undici refuses it).

**Client IP (trusted proxies)**: per-IP rate limits and request logs use the real client IP. The proxy rebuilds `X-Forwarded-For` with only the client IP (`lib/client-ip.ts`): the incoming header is believed only when the TCP peer is in `TRUSTED_PROXIES` (Caddy in production), otherwise the socket address is used. The API sets Fastify `trustProxy` from its own `TRUSTED_PROXIES` (`apps/api/src/config/trusted-proxies.ts`), so it believes the header only from `web`. Both default to `loopback,uniquelocal` (localhost in dev; `none` trusts no one). In production `web` trusts Caddy only: `TRUSTED_PROXIES` also accepts host names, resolved through DNS every 30 s (`TrustedProxies`, trusting nobody while a name doesn't resolve), and the compose file sets `caddy` (`WEB_TRUSTED_PROXIES`, #183), so another container on the shared `proxy` network can't choose its client IP; Caddy itself sees the device's Tailscale address (`100.x` or `fd7a:115c:a1e0::…`) only because `proxy` is dual-stack (infra repo, #251: on an IPv4-only network, IPv6 connections arrive from the Docker gateway through `docker-proxy`); `api` trusts the private ranges of the project network, which is only safe because no port of the production stack is published: never publish the API port. A client sending its own `X-Forwarded-For` can't leave its rate-limit bucket (`trust-proxy.spec.ts`, `client-ip.test.ts`). SSR calls made by the web server itself (loaders, the deduplicated refresh) carry no client IP and count against the web server's address.

**SSR session renewal**: `getMe` (`lib/auth.ts`) resolves the user with `resolveServerSession` (`lib/server-session.ts`): with a valid `token` it just calls `/api/auth/me`; when the access token is missing/expired and a `refresh_token` is present it calls `POST /api/auth/refresh` server-side, appends the rotated `Set-Cookie` headers to the page response, and makes later loaders in the same request use the new cookies. Refreshes are deduplicated per refresh token inside the web process (in-flight calls share one rotation, and a successful one is replayed for 10 s), and the proxied `POST /api/auth/refresh` goes through the same path, so concurrent reloads/tabs or a client refresh racing a reload never trip the API's reuse detection. This assumes a single web instance; the API's rotation and reuse detection are unchanged.

**Authenticated layout**: every signed-in page lives under the pathless layout route `routes/_app.tsx` (files in `routes/_app/`). Its `beforeLoad` guard (`requireUser` in `apps/web/src/lib/auth-guard.ts`) redirects anonymous visitors to `/auth` during SSR, before any protected markup renders (after trying to renew an expired access token, see SSR session renewal), and exposes `user` through the route context. The shell (`apps/web/src/components/app-shell/`) is the `@finances/ui` sidebar (a sheet below `md`, opened from a top bar); add a section by creating `routes/_app/<name>.tsx` and an entry in `app-shell/nav-items.ts` (`NAV_ITEMS`). Settings pages are not in that list (#261): they live under the pathless `routes/_app/_settings.tsx` (files in `routes/_app/_settings/`). **Réglages** (#300, `/settings`, `components/settings/SettingsPage.tsx`) is one list of sections like iOS Settings (`SettingsGroup` / `SettingsLinkRow` / `SettingsControlRow` in `components/settings/SettingsList.tsx`: a card per group, rows with a tinted icon, the name and its current state under it, ›): Compte (`/settings/account`: the name edited in place, saved on blur or Enter with a toast offering « Annuler », the email as text, « Membre depuis »), Apparence (`ThemeChoice`, three segments in the row, no screen), Sécurité (`/settings/security`: `ChangePasswordCard`, `PasskeysCard`, `SessionsCard`), Catégories and Règles (their pages, URLs unchanged), Claude et accès (`/settings/access`, #329, `components/access/`: « Ce que Claude peut faire », « Connecter Claude » (« Claude sur ce Mac », « Claude sur le téléphone et claude.ai » while remote access is on, « Script ou autre outil »), a stepped `ConnectSheet` (« Lire seulement » / « Lire et classer », the duration, then the token once inside a ready-to-paste `claude_desktop_config.json` and `claude mcp add` (`mcp-setup.ts`: the page's origin as `FINANCES_API_URL`, the server path remembered in `localStorage`), never stored), then one list « Accès actifs » of tokens and grants whose detail (`AccessDetailSheet`) renames a token (`PATCH /api/access-tokens/:id`), revokes behind a confirmation and tells its calls in plain words (`access-labels.ts`, one sentence per route open to tokens; `GET /api/access-tokens/audit?tokenId=`)), « Se déconnecter » (a row of its own, kept with the sidebar’s button), Zone dangereuse (`/settings/danger`: `DeleteAccountCard`, last, alone). ### PWA

- **Manifest** `apps/web/public/manifest.json` (`start_url: /dashboard`, shortcuts to Tableau de bord / Opérations / À revoir / Import), linked from `__root.tsx` with the iOS meta tags and light/dark `theme-color` (light `--background` `#f4f7fc`, dark `#090c1a`; update them, the manifest and `offline.html` together if the theme changes).
- **Icons** (`public/icons/*.png`, `public/favicon.ico`) are generated from `public/logo.svg` by `pnpm --filter @finances/web icons` (`apps/web/scripts/generate-icons.mjs`, `sharp`) and committed; re-run it when the logo changes.
- **Service worker**: a small hand-written worker (`src/sw/worker/service-worker.ts`, decisions in `src/sw/routing.ts`, unit tested), bundled into `/sw.js` by the Vite plugin `apps/web/plugins/service-worker.ts` in **production client builds only** (not `vite dev`), and registered by `components/pwa/ServiceWorkerUpdates.tsx` only when `import.meta.env.PROD` and on a secure context (HTTPS or localhost). `vite-plugin-pwa` was not used: the plugin only touches the client environment, so the Nitro SSR bundle and the `/api` server route are unaffected.
  - **Cached** (precache, cache-first): the hashed client assets (JS/CSS) of the build and the shell files listed in `src/sw/precache.ts` (`offline.html`, manifest, icons, favicon, logo). The cache is named `finances-shell-<content hash>`; a new build gets a new name and older caches are deleted when it activates.
  - **Never cached**: `/api/*` (not even intercepted), non-GET and cross-origin requests (Google Fonts included), any other same-origin URL, and server-rendered pages: navigations go network-first and fall back to the static `offline.html` ("Hors ligne", no data) only when the network fails. Requests made by the worker carry no cookies. So nothing sensitive is ever in Cache Storage, before or after logout. Keep it that way: do not add runtime caching of pages or API responses.
  - **In-app navigations** are client-side and never reach the worker's offline fallback. Offline, the guard's `fetchCurrentUser` throws instead of returning null (never a redirect to `/auth`): at once, without a request, when `navigator.onLine` is false (iOS holds requests while offline), and after 8 s otherwise (`loadCurrentUser` in `lib/current-user.ts`), and the router's `defaultErrorComponent` (`components/RouteError.tsx`) shows "Hors ligne" with "Réessayer" (`router.invalidate()`) and retries by itself on `online`; any other guard/loader error gets a generic French page. A thin bar (`app-shell/NavigationProgress.tsx`) shows while a navigation is pending, and a generic page skeleton (`components/PagePending.tsx`, `defaultPendingComponent`) replaces the previous page after 1 s.
  - **Updates**: a new worker waits; the app shows a "Nouvelle version disponible" toast and, on "Recharger", the worker skips waiting and open pages reload. Waiting (rather than `skipWaiting` on install) keeps an open old page from lazy-loading chunks that the new deploy no longer serves. Installed apps re-check for updates when brought back to the foreground (at most hourly).
- **HTTP cache policy**: the API sends `Cache-Control: no-store` (+ `Pragma: no-cache`, `Expires: 0`) on every `/api` response (`onSend` hook, `apps/api/src/common/http/no-store.ts`). On the web server, a global request middleware in `apps/web/src/start.ts` applies `lib/cache-policy.ts` to everything the Start handler answers: `/api/*` (proxy) gets the same headers, every page and server function (signed-in pages, `/auth`, `/`, redirects, errors) gets `private, no-store`, so nothing private lands in the HTTP or back/forward cache. Static files are served by Nitro before that handler: `/assets/*` keeps `public, max-age=31536000, immutable`, `sw.js` and `manifest.json` get `no-cache` (Nitro `routeRules` in `vite.config.ts`) so deploys are picked up. Logout answers `Clear-Site-Data: "cache"` only: `"storage"` would unregister the service worker and wipe its non-sensitive shell cache and the theme preference, and the session cookies are already cleared explicitly. `src/start.ts` replaces Start's default request middleware, so it restates the CSRF middleware for server functions: keep it.
- **Security headers** (#174): the same middleware chain (`src/start.ts`) gives every page, redirect and server function (not `/api`, which keeps the API's helmet headers) a Content-Security-Policy and `X-Frame-Options: DENY` (`lib/security-headers.ts`). `script-src` is `'self'` + a per-response nonce + the hashes of the app's inline `<head>` scripts (`lib/inline-scripts.ts`): the nonce goes to TanStack through the request context and `router.options.ssr.nonce` (`lib/csp-nonce.ts`), and the client reads it back from `<meta property="csp-nonce">`. Never add `'unsafe-inline'` or `'unsafe-eval'` to `script-src` (dev only adds `ws:` for HMR): a new inline script goes in `inline-scripts.ts`, and Zod runs jitless (set there) so it never probes `new Function`. `style-src` keeps `'unsafe-inline'` (server-rendered `style` attributes, runtime `<style>` from Radix / toasts) plus Google Fonts; `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `connect-src` / `worker-src 'self'`. The static `offline.html` gets its own hash-only CSP from a Nitro route rule (`plugins/offline-csp.ts`). `e2e/csp.spec.ts` loads pages and fails on any violation. They also get `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin` and a `Permissions-Policy` denying the features the app never uses (camera, microphone, geolocation, payment, USB, ...; `PERMISSIONS_POLICY`), passkeys allowed on `self` only, the clipboard left at its default (#204, `crossOriginHeaders`); the OAuth consent flow (`/oauth/authorize`, `/auth?redirect=` to it: `keepsOpener`) gets no COOP so the Claude app's popup keeps its opener. `offline.html` gets the same three, static files CORP (Nitro route rule `/**`), and the API helmet's COOP / CORP plus its own `Permissions-Policy` (`common/http/permissions-policy.ts`). No `Cross-Origin-Embedder-Policy`: it would block Google Fonts.
- **Testing**: unit tests cover the routing/precache logic. To check the worker itself, `pnpm --filter @finances/web build` and run `node .output/server/index.mjs` against a throwaway database, open `http://localhost:3000` (secure context), then in DevTools > Application inspect the manifest, the service worker and Cache Storage (only `finances-shell-*` with `/assets/*` and shell files), and tick "Offline" to see the offline page.

## MCP server (`apps/mcp`)

Local MCP server for Claude Desktop / Claude Code (official TypeScript SDK, stdio transport, setup in [`apps/mcp/README.md`](apps/mcp/README.md)). Configured with `FINANCES_API_URL` and `FINANCES_API_TOKEN` (a personal access token: `read` for the read tools, `write` for the write tools). Rules:

- **API only**: tools call `/api/*` with `Authorization: Bearer`, never the database or `apps/web` code. Read tools (`GET`, plus the read-only `POST /budgets/suggest`) keep working with a `read` token; write tools get a clear "lecture seule" error with one.
- **Write tools** (#77, `tools/*-writes.ts`: `add_transaction`, `categorize_transactions`, `mark_one_off`, `set_transaction_note`, `create_rule`, `set_budget_targets` (expense targets and planned income, #315; its preview says what the plan leaves to save); `close_months`, #342; `set_invested_amount`, #358 and #360: an investment account's invested base (not an exchange), its preview the invested amount, result and rate now → after; `split_transaction`, #357: parts by category name or slug and euros as text, its preview giving each part's kind (« remboursement de Restaurants », « revenu Remboursements ») and the effect on the month's budget lines, French error when the parts don't add up; undone in the app or by `categorize_transactions`): without `confirm: true` they only read and return a preview of exactly what would change (current state of the selection through `GET /transactions?ids=`); with `confirm: true` they re-read and apply only what still differs, so a repeated call changes nothing more (a manual transaction with the same day, amount and account is refused unless `allowDuplicate`), then list what changed with an undo hint. **No delete tools**: undoing a created transaction, rule or new budget line is done in the app. Annotated `readOnlyHint: false`, `destructiveHint: false`.
- **Bank imports** (#103, `tools/import-writes.ts`): `preview_bank_import` uploads a CIC CSV (a local `.csv` path ≤ 5 MB sent as is, or text sent as UTF-8 with a BOM) to `POST /imports/preview` (writes no transaction), `commit_bank_import` commits it only with `confirm: true` (conflicts only with `includeConflicts`; an already committed preview is a no-op) and lists the import's review-queue rows with their ids; `list_imports` reads `GET /imports`. Only `POST /imports/preview` and `/imports/:id/commit` are open to `write` tokens (`@TokenAccess('write')`); discarding or undoing an import stays session-only.
- **Closing months** (#342, `tools/month-close-writes.ts`): `close_months` takes `month`, or `allBefore: true` (every past month left open since the first month ever closed, up to the previous Europe/Paris month, from `GET /month-close`; `from` is required when no month was ever closed, so the pre-app history is never reached by default), at most 24 months per call. Without `confirm: true` it previews each month (already closed / to close, the steps still open from `GET /month-close/:month`); with it, it closes the open months oldest first (`POST /month-close/:month/close`, a 409 counts as already closed). No reopen tool: « Revue du mois › Rouvrir » in the app.
- **Prompt** `revue_du_mois` ("Revue du mois", `src/prompts.ts`): walks through the month-end review with `month_close_status` (`GET /month-close/:month`), `list_imports` and the import tools, `review_queue`, the write tools and `set_budget_targets` for next month, then `close_months` after the owner agrees to its preview; investment values, ticking steps and reopening stay in the app.
- **Invested amounts** (#358, #360): `list_investment_accounts` gives every account's invested amount (« investi »), result and rate, and the coins of unknown cost; `set_invested_amount` sets the base of a PEA, a life insurance, employee savings or a wallet or manual crypto account (removing it stays in the app).
- **Transfer links** (#296): `search_transactions` shows a transfer's other account (`→ PEA` / `← PEA`); `savings_and_goals` says where the invested contributions come from and adds « où est allé l'argent » (`GET /investments/flows`) and the coins sent between crypto accounts with their cost (`GET /investments/movements`). Read only: links are set in the app.
- **Investment tools** (#104, `tools/investments.ts`, `tools/investment-writes.ts`, prompt `importer_mes_investissements` in `src/investments-prompt.ts`, setup in [`docs/runbooks/investments-from-drive.md`](docs/runbooks/investments-from-drive.md)): Claude reads the owner's statements with its own Google Drive connector and writes only the extracted values; the app has no Google credentials and makes no Google call. `list_investment_accounts` (read), `add_investment_snapshots` (`POST /accounts/:id/snapshots/bulk`, new / replaced / unchanged days and the net-worth effect; contributions ride on the snapshots, so there is no contributions tool), `sync_crypto_holdings` (quantities as exact decimal strings, `src/quantity.ts`; owns only the `manual` lines of one location: `import` / `sync` lines are never touched, missing manual lines are set to 0 through `PUT`, never deleted; `POST|PUT /accounts/:id/holdings[/:holdingId]` are `@TokenAccess('write')` for it, and a token may only touch the `manual` lines of a `manual`-source account: `CryptoService.assertTokenMayWrite` answers 403 for exchange / wallet accounts and import / sync lines; the tool refuses those accounts up front) and `create_investment_account` (read only: `POST /accounts` stays session-only, it says what to create in the app).
- **Types** come from `apps/api/openapi.json` via `@hey-api/openapi-ts` (types only) into the git-ignored `src/api/generated/` (`@finances/mcp#generate` depends on `@finances/api#generate`); the fetch client is `src/api/client.ts`, which maps 401/403/409/429/5xx/unreachable to French messages returned as tool errors.
- **Output**: French text, euros formatted from cents at the edge (`src/format.ts`), calendar dates as `dd/mm/yyyy` without time zone conversion, "today" in Europe/Paris; partial months are stated with `periodNote`. Small input schemas (≤ 10 fields), names rather than ids for accounts and categories (`tools/lookup.ts`); transactions are shown with their id, which the write tools take. Amounts typed by the model are parsed from text into cents (`parseEuros`), never through a float.
- **Privacy**: stdout is the MCP channel (ESLint forbids `console.log`); stderr gets only a tool name and an HTTP status, never arguments, outputs, amounts, labels or the token.
- **Remote transport** (#78, #328, off by default): `node dist/index.js --http` (`src/http/`) serves `POST /mcp` statelessly (one `McpServer` + `StreamableHTTPServerTransport` per request, JSON responses), the protected resource metadata, and relays the OAuth endpoints to the API (form → JSON). Only `fin_oat_` tokens, checked with `GET /api/oauth/token-info` (cached 30 s) and forwarded to the API; 401 with `resource_metadata`; Origin check, per-IP and per-token limits (`RateLimiter`), client IP from `MCP_TRUSTED_PROXIES` only (IPs, ranges or host names resolved every 30 s like `web`'s, `TrustedProxies` in `src/http/client-ip.ts`); refuses to start unless `REMOTE_MCP_ENABLED=true`. `ToolContext.remote` makes tools avoid the server's disk (`preview_bank_import` refuses `filePath`). In production (#328) it is the `finances-mcp` service (image `ghcr.io/gregoirebdn/finances-mcp` from `apps/mcp/Dockerfile`), started only with the `remote-mcp` compose profile; the `infra` repo serves its seven paths on a public host restricted to Anthropic's range (runbook § 3).
- **Tests**: Vitest with synthetic fixtures through a real MCP client over `InMemoryTransport` and a mocked `fetch` (`src/test/mock-api.ts`); no database.

## Containerisation

```bash
# Dev — starts PostgreSQL + Mailpit (apps run on the host)
docker compose up -d

# Production images built from this checkout, stack run locally under a throwaway
# project name (the dev stack is also called `finances`; never omit -p locally)
FINANCES_VERSION=local docker compose -p finances-local --env-file <env> \
  -f docker-compose.prod.yml -f docker-compose.build.yml up --build -d
```

`docker-compose.yml` exposes PostgreSQL on `localhost:5432` and Mailpit (SMTP `localhost:1025`, UI `localhost:8025`) with credentials matching the defaults in `apps/api/.env.example`.

**Production stack** (`docker-compose.prod.yml`, runbook [`docs/runbooks/production-stack.md`](docs/runbooks/production-stack.md), deploys [`docs/runbooks/deploy.md`](docs/runbooks/deploy.md)):

- Compose project `name: finances`, deployed in `/srv/finances` (owned by the `deploy` user) with the compose file of the deployed tag and a mode-600 `.env`. Every variable is documented in [`.env.production.example`](.env.production.example); required ones use `${VAR:?}` so the stack refuses to start without them.
- Services `db` (`postgres:17-alpine`, volume `db_data`), `api`, `web`, and `finances-mcp` (the remote MCP adapter, #328) only with the `remote-mcp` profile (`COMPOSE_PROFILES=remote-mcp` in `.env`, with `REMOTE_MCP_ENABLED=true`, which `deploy.sh` checks), all `restart: unless-stopped` with healthchecks (`web` checks the whole chain through `/api/health`; `finances-mcp` a TCP connect on 4100). **No `ports:` on any service**: `web` also joins the external `proxy` network with the alias `finances-web`, which the server's Caddy (`infra` repo) targets as `finances-web:3000`; `api` and `db` stay on the project network; `finances-mcp` joins `proxy` too (Caddy targets `finances-mcp:4100` from the public host) and believes `X-Forwarded-For` from `caddy` only (`MCP_TRUSTED_PROXIES`). Never publish a port of this stack (the API trusts forwarded client IPs from private addresses, #49).
- Images `ghcr.io/gregoirebdn/finances-{api,web,mcp}:${FINANCES_VERSION}` (`vX.Y.Z` or `sha-<shortsha>`). `docker-compose.build.yml` adds `build:` sections (`pull_policy: build`) to build them from the checkout instead. `deploy.sh` pulls, health-checks and rolls back `finances-mcp` when its profile is on (`test-deploy.sh` covers it).
- Migrations: `docker compose -f docker-compose.prod.yml run --rm api node dist/database/migrate.js` (`apps/api/src/database/migrate.ts`, Drizzle's runtime migrator; the image ships `drizzle/` through the API package's `files`). Seed: `... run --rm api node dist/database/seed.js`. Both are idempotent and run on every deploy.
- **Hardening** (#183, `x-hardening` in the compose file): `api`, `web` and `finances-mcp` run as `node` with `read_only: true` (only a 16 MB `/tmp` tmpfs is writable), `cap_drop: [ALL]`, `no-new-privileges`, `mem_limit` = `memswap_limit` = `APP_MEM_LIMIT` (default `512m`) and `pids_limit: 256` (`finances-mcp`: `MCP_MEM_LIMIT`, default `256m`, and 128); `db` keeps only `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID` with `no-new-privileges`. Runtime code must never write outside `/tmp`. The API accepts an incoming `X-Request-Id` only when it is a UUID (`genReqId`, `config/logger.ts`), else it mints one.
- The API image sets `NODE_ENV=production` (session cookies `Secure`) and `HOST=0.0.0.0` (Fastify listens on localhost otherwise). SMTP is optional in production: without `SMTP_HOST` no email is sent and `/api/health` leaves SMTP out; when it is configured, an unreachable SMTP server fails the health check (and a deploy).

The browser only talks to the `web` service: it proxies `/api/*` to the `api` service (`API_URL=http://api:4000`, set in the compose file) and calls it directly during SSR. Caddy forwards everything, `/api` included, to `web`; routing `/api` straight to `api` would bypass the web process's refresh deduplication for client-side refreshes.

The Dockerfiles (`apps/api/Dockerfile`, `apps/web/Dockerfile`, `apps/mcp/Dockerfile`) use multi-stage builds with the monorepo root as context (`.dockerignore` keeps `data/`, `.env*` and `.claude/` out of it). The API and the MCP adapter use `pnpm deploy --prod --legacy`, which copies the package's `files` (`dist`, `drizzle`) and its production dependencies, so anything `dist/` requires at runtime must be in `dependencies`. The web image copies only the Nitro `.output/` directory; a package imported by `@finances/ui` that bundles CommonJS code requiring `react` (e.g. `recharts`) must also be a dependency of `apps/web`, or the SSR bundle keeps a runtime `require('react')` that fails in the image. Nitro bundles the server and traces only its external packages into `.output/server/node_modules`; its built-in list of native / non-bundleable packages would also pull in any of them that merely resolves (vite, esbuild, sharp, playwright, turbo, ...), so `apps/web/plugins/server-trace.ts` (#242) excludes the workspace's tooling (`traceDeps: ['!pkg']`) and fails the build when anything outside `SERVER_RUNTIME_PACKAGES` (today `tslib`) is traced: exclude a new tool there, or add a real runtime external deliberately.

Target deployment (M6): a VPS running the production compose stack, reachable only through Tailscale. The hosting decisions (Compose per app + one server-level Caddy on a shared `proxy` network, server config in a separate `infra` repo, own domain on the tailnet, one Postgres per app, GHCR images, deploys over Tailscale, restic backups) are in [`docs/adr/0001-multi-app-hosting.md`](docs/adr/0001-multi-app-hosting.md).

## Environment setup (API)

Copy `apps/api/.env.example` to `apps/api/.env` and fill in:

- `DATABASE_URL` — PostgreSQL connection string (default targets the dev Docker container)
- `JWT_SECRET` — JWT signing secret; required in production and at least 32 characters (`openssl rand -hex 32`), or the API refuses to boot (#182); outside production an ephemeral one is generated when unset
- `APP_URL` — web app origin (default: `http://localhost:3000`), used in email links and as the CORS origin
- `TRUSTED_PROXIES` — peers allowed to set the client IP through `X-Forwarded-For` (default `loopback,uniquelocal`, see Client IP)
- `WEBAUTHN_RP_ID`, `WEBAUTHN_ORIGIN` — passkeys relying party; empty = `APP_URL`'s host name and origin (see Passkeys)
- `REMOTE_MCP_ENABLED`, `REMOTE_MCP_PUBLIC_URL`, `REMOTE_MCP_REDIRECT_URIS` — remote MCP OAuth (#78), off by default (see Remote MCP OAuth)

The web app reads two runtime variables (see `apps/web/.env.example`), never exposed to the browser: `API_URL`, the API origin as reached from the web server (default `http://localhost:4000`), and `TRUSTED_PROXIES` (see Client IP).

- SMTP config (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`) — defaults target the dev Mailpit container; in production `SMTP_HOST` is optional (unset = no email)
- Crypto prices (`PRICE_API_ENABLED`, `PRICE_API_URL`, `PRICE_CACHE_TTL_SECONDS`) — default to the CoinGecko public API with a 10-minute cache (see Crypto prices)

Never put real credentials or real financial data in `.env.example`.
