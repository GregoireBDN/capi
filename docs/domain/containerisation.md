# Containerisation and network

Feature details moved out of [`CLAUDE.md`](../../CLAUDE.md) (#422). The domain rules, workflow conventions and architecture there apply here too.

## Client IP (trusted proxies)

**Client IP (trusted proxies)**: per-IP rate limits and request logs use the real client IP. The proxy rebuilds `X-Forwarded-For` with only the client IP (`lib/client-ip.ts`): the incoming header is believed only when the TCP peer is in `TRUSTED_PROXIES` (Caddy in production), otherwise the socket address is used. The API sets Fastify `trustProxy` from its own `TRUSTED_PROXIES` (`apps/api/src/config/trusted-proxies.ts`), so it believes the header only from `web`. Both default to `loopback,uniquelocal` (localhost in dev; `none` trusts no one). In production `web` trusts Caddy only: `TRUSTED_PROXIES` also accepts host names, resolved through DNS every 30 s (`TrustedProxies`, trusting nobody while a name doesn't resolve), and the compose file sets `caddy` (`WEB_TRUSTED_PROXIES`, #183), so another container on the shared `proxy` network can't choose its client IP; Caddy itself sees the device's Tailscale address (`100.x` or `fd7a:115c:a1e0::…`) only because `proxy` is dual-stack (infra repo, #251: on an IPv4-only network, IPv6 connections arrive from the Docker gateway through `docker-proxy`); `api` trusts the private ranges of the project network, which is only safe because no port of the production stack is published: never publish the API port. A client sending its own `X-Forwarded-For` can't leave its rate-limit bucket (`trust-proxy.spec.ts`, `client-ip.test.ts`). SSR calls made by the web server itself (loaders, the deduplicated refresh) carry no client IP and count against the web server's address.

## Production stack

**Production stack** (`docker-compose.prod.yml`, runbook [`docs/runbooks/production-stack.md`](../runbooks/production-stack.md), deploys [`docs/runbooks/deploy.md`](../runbooks/deploy.md)):

- Compose project `name: finances`, deployed in `/srv/finances` (owned by the `deploy` user) with the compose file of the deployed tag and a mode-600 `.env`. Every variable is documented in [`.env.production.example`](../../.env.production.example); required ones use `${VAR:?}` so the stack refuses to start without them.
- Services `db` (`postgres:17-alpine`, volume `db_data`), `api`, `web`, and `finances-mcp` (the remote MCP adapter, #328) only with the `remote-mcp` profile (`COMPOSE_PROFILES=remote-mcp` in `.env`, with `REMOTE_MCP_ENABLED=true`, which `deploy.sh` checks), all `restart: unless-stopped` with healthchecks (`web` checks the whole chain through `/api/health`; `finances-mcp` a TCP connect on 4100). **No `ports:` on any service**: `web` also joins the external `proxy` network with the alias `finances-web`, which the server's Caddy (`infra` repo) targets as `finances-web:3000`; `api` and `db` stay on the project network; `finances-mcp` joins `proxy` too (Caddy targets `finances-mcp:4100` from the public host) and believes `X-Forwarded-For` from `caddy` only (`MCP_TRUSTED_PROXIES`). Never publish a port of this stack (the API trusts forwarded client IPs from private addresses, #49).
- Images `ghcr.io/gregoirebdn/finances-{api,web,mcp}:${FINANCES_VERSION}` (`vX.Y.Z` or `sha-<shortsha>`). `docker-compose.build.yml` adds `build:` sections (`pull_policy: build`) to build them from the checkout instead. `deploy.sh` pulls, health-checks and rolls back `finances-mcp` when its profile is on (`test-deploy.sh` covers it).
- Migrations: `docker compose -f docker-compose.prod.yml run --rm api node dist/database/migrate.js` (`apps/api/src/database/migrate.ts`, Drizzle's runtime migrator; the image ships `drizzle/` through the API package's `files`). Seed: `... run --rm api node dist/database/seed.js`. Both are idempotent and run on every deploy.
- **Hardening** (#183, `x-hardening` in the compose file): `api`, `web` and `finances-mcp` run as `node` with `read_only: true` (only a 16 MB `/tmp` tmpfs is writable), `cap_drop: [ALL]`, `no-new-privileges`, `mem_limit` = `memswap_limit` = `APP_MEM_LIMIT` (default `512m`) and `pids_limit: 256` (`finances-mcp`: `MCP_MEM_LIMIT`, default `256m`, and 128); `db` keeps only `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID` with `no-new-privileges`. Runtime code must never write outside `/tmp`. The API accepts an incoming `X-Request-Id` only when it is a UUID (`genReqId`, `config/logger.ts`), else it mints one.
- The API image sets `NODE_ENV=production` (session cookies `Secure`) and `HOST=0.0.0.0` (Fastify listens on localhost otherwise). SMTP is optional in production: without `SMTP_HOST` no email is sent and `/api/health` leaves SMTP out; when it is configured, an unreachable SMTP server fails the health check (and a deploy).

## Staging stack

**Staging stack** (#421, runbook [`docs/runbooks/staging.md`](../runbooks/staging.md)): every push to `main` runs `.github/workflows/staging.yml`: CI (`ci.yml` as a reusable workflow), the three images built, scanned with Trivy and pushed as `sha-<short>`, then, in the `staging` environment (no required reviewer, `concurrency: deploy-staging`), `deploy.sh --staging sha-<short>` over Tailscale.

- `docker-compose.prod.yml` + the override [`docker-compose.staging.yml`](../../docker-compose.staging.yml) (`name: finances-staging`), deployed in `/srv/finances-staging` with its own mode-600 `.env` ([`.env.staging.example`](../../.env.staging.example)), volume (`finances-staging_db_data`) and secrets, and its own host (`APP_URL`), so it shares no database, cookie origin or secret with production. No port, no backup.
- The override fixes what staging must never change through `.env`: the database `finances_staging` with `DEMO_STAGING_DATABASE` naming it (the demo guard accepts `NODE_ENV=production` only there, never on `finances`), SMTP, remote MCP, the price API and wallet sync off, `web`'s `APP_ENVIRONMENT=staging` (#454: yellow header, icons and manifest, [PWA](pwa.md)), and `web`'s alias on `proxy` replaced (`!override`, a plain list would be merged) by `finances-staging-web`, Caddy's staging upstream.
- `deploy.sh --staging`: always `-p finances-staging`, version `sha-<hex>` only (production keeps `vX.Y.Z`), both compose files installed and restored together; it refuses a merged config that keeps `finances-web` and the MCP profile, and after the seed wipes the database and seeds the demo data again (`seed-demo.js --reset`, one transaction, before `up`). `test-deploy.sh` covers it.

The browser only talks to the `web` service: it proxies `/api/*` to the `api` service (`API_URL=http://api:4000`, set in the compose file) and calls it directly during SSR. Caddy forwards everything, `/api` included, to `web`; routing `/api` straight to `api` would bypass the web process's refresh deduplication for client-side refreshes.

The Dockerfiles (`apps/api/Dockerfile`, `apps/web/Dockerfile`, `apps/mcp/Dockerfile`) use multi-stage builds with the monorepo root as context (`.dockerignore` keeps `data/`, `.env*` and `.claude/` out of it). The API and the MCP adapter use `pnpm deploy --prod --legacy`, which copies the package's `files` (`dist`, `drizzle`) and its production dependencies, so anything `dist/` requires at runtime must be in `dependencies`. The web image copies only the Nitro `.output/` directory; a package imported by `@capi/ui` that bundles CommonJS code requiring `react` (e.g. `recharts`) must also be a dependency of `apps/web`, or the SSR bundle keeps a runtime `require('react')` that fails in the image. Nitro bundles the server and traces only its external packages into `.output/server/node_modules`; its built-in list of native / non-bundleable packages would also pull in any of them that merely resolves (vite, esbuild, sharp, playwright, turbo, ...), so `apps/web/plugins/server-trace.ts` (#242) excludes the workspace's tooling (`traceDeps: ['!pkg']`) and fails the build when anything outside `SERVER_RUNTIME_PACKAGES` (today `tslib`) is traced: exclude a new tool there, or add a real runtime external deliberately.

Target deployment (M6): a VPS running the production compose stack, reachable only through Tailscale. The hosting decisions (Compose per app + one server-level Caddy on a shared `proxy` network, server config in a separate `infra` repo, own domain on the tailnet, one Postgres per app, GHCR images, deploys over Tailscale, restic backups) are in [`docs/adr/0001-multi-app-hosting.md`](../adr/0001-multi-app-hosting.md).
