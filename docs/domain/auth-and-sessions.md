# Auth and sessions

Feature details moved out of [`CLAUDE.md`](../../CLAUDE.md) (#422). The domain rules, workflow conventions and architecture there apply here too.

## Auth (single user)

**Auth (single user)**: password auth, plus passkeys (below) — no OAuth. The owner account is created through the normal sign-up form on first launch; as soon as one user exists, `POST /api/auth/register` returns 403 (re-checked under a Postgres advisory lock so concurrent sign-ups can't create a second account) and `GET /api/auth/registration-status` returns `{ open: false }`, which the web app uses to hide sign-up. Email verification (`verify-email`, `resend-verification`) is kept when SMTP is configured; without SMTP (production without `SMTP_HOST`) the owner is created already verified, and an existing unverified owner is marked verified the next time `GET /api/auth/me` loads, since no verification email could ever arrive. Cookie-based JWT (`httpOnly`, `sameSite: lax`, `Secure` in production): the `token` cookie holds a short-lived (15 min) access JWT, and a rotating `refresh_token` cookie (path `/`, 30 days) renews it via `POST /api/auth/refresh`. **Cookie names** (#217, `session-cookies.ts`, `sessionCookieConfig`): in production they are `__Host-token` / `__Host-refresh_token` (no `Domain`, `Path=/`, `Secure`: a sibling subdomain can't toss its own); outside production they keep the plain names, since `Secure` cookies can't be set over HTTP (the phone on `vite dev --host`). Read them only through `readAccessCookie` / `readRefreshCookie` and set or clear them through `setSessionCookies` / `clearSessionCookies`. In production the API reads them under their `__Host-` names only (#226) and every reply that sets or clears the session clears any leftover plain pair. The web server reads either name, `__Host-` first (`ACCESS_COOKIES` / `REFRESH_COOKIES` in `lib/server-session.ts`), and presents a refresh cookie under the name the browser sent; presenting an already-rotated refresh token revokes the whole family (reuse detection). The rotation revokes the presented token with a conditional `UPDATE ... WHERE revoked_at IS NULL RETURNING`, so of two refreshes racing with one token only one revokes it (#178). **Grace for a lost response** (#292): a token rotated less than `SESSION_REFRESH_REUSE_GRACE_MS` (60 s) ago whose successors (`refresh_tokens.parent_id`) are all unused gets one more successor instead of burning the family (the loser of a race, a response lost to the network, an iOS suspension or a web restart); renewing one of those siblings drops the others (`superseded`), so a later use of a dropped one, or of the old token after the grace or once a successor was used, is still reuse. Revocations keep their reason (`refresh_tokens.revoked_reason`: `rotated`, `superseded`, `reuse`, `lifetime`, `logout`, `signed_out`, `password`); every refused refresh is logged with its reason only (`Session refresh refused: unknown | expired | reuse | lifetime | revoked | no cookie`), every session end with its kind, never a token, id or user. **Only a 401 means signed out** (#292; `GET /api/auth/me` answers 401, never an empty 200, for a token whose user no longer exists: a deleted account or a reset database): on the web, `me` and the refresh answering 429, 5xx or nothing are retried (`Retry-After` honoured, capped) then shown as the error page with « Réessayer » (`SessionUnavailableError`, `lib/session-errors.ts`), never as a redirect to `/auth`: `currentUserFromResult` / `loadCurrentUser` (`lib/current-user.ts`, one retry), the browser refresh (`lib/session-refresh.ts`, 3 tries, a transient failure handed to the caller as its own status, never the 401), and the SSR path (`resolveServerSession` returns `unavailable`, `getMe` forwards the rotated cookies then throws). The guard's signed-in answer is reused for `CURRENT_USER_CACHE_MS` (10 s, in-flight calls shared, dropped on logout and on a refused refresh): the router preloads on intent, and every hovered or touched link ran the `_app` guard's `GET /api/auth/me` against its 60 / min limit. A family has an **absolute lifetime** of 90 days from its password or passkey sign-in (`refresh_tokens.authenticated_at`, else its first token; `SESSION_MAX_LIFETIME_MS`): after that the refresh answers 401 and revokes the family, and no renewed token expires later than that end. **The browser never calls the API origin directly**: the web server proxies `/api/*` to the API (see Web architecture in [`CLAUDE.md`](../../CLAUDE.md#web-architecture-tanstack-start)), so both cookies are first-party to the web origin. `refresh_token` is scoped to `/` (not `/api/auth`) so page requests carry it to the web SSR guard, which renews an expired access token server-side; the API also clears any leftover cookie at the old `/api/auth` path whenever it sets or clears the session. Passwords are hashed with `bcryptjs`. **New passwords** (sign-up, reset, change: `NewPasswordField` in `auth/dto/fields.ts`, `newPasswordField` in the web's `auth.schemas.ts`) need at least 12 characters and at most 72 bytes (bcrypt ignores the rest); sign-in and "current password" accept any stored password. Forms that take a password (sign-in, sign-up, forgotten password, reset, change, `ReauthSheet`) are `method="post"` and keep their submit button disabled until hydration (`useHydrated`, `lib/use-hydrated.ts`, #203): server-rendered, they would otherwise be submitted natively as a GET with the password in the URL; `e2e/no-js-forms.spec.ts` submits them with JavaScript off. An unknown email still runs one bcrypt comparison against a dummy hash, so a failed sign-in takes as long either way. Password reset goes through `forgot-password` / `reset-password` (tokens handled in `apps/api/src/email/tokens.ts`): only the latest link works (a new one spends the pending ones) and only once, and a reset **ends every session** (all refresh-token families). `POST /api/auth/change-password` (#177, session only, fresh session + current password, throttled like the login; `ChangePasswordCard` in Réglages › Sécurité) ends every **other** family and keeps the one whose `refresh_token` made the change. Both take `revokeAccessTokens` to revoke the personal access tokens too. Access JWTs already issued stay valid until they expire (15 minutes). **Sessions** (#217, `auth/sessions/`, ASVS 3.3.4): `GET /api/auth/sessions` lists the active refresh-token families (sign-in method `password` / `passkey` / `sign_up`, sign-in time, last renewal, expiry, a coarse device such as « Safari · iPhone » from `describeDevice`, the current one first; then the families burned by reuse detection in the last 30 days, with `reuseDetectedAt`, shown as « Déconnecté : réutilisation détectée » without an action, #292; `refresh_tokens.sign_in_method` and `device` are set at sign-in and copied on rotation, never the raw User-Agent, and never a token or hash in the response) and `DELETE /api/auth/sessions/:id` (fresh session) revokes a family, so that device is signed out at its next refresh; both session-only. The web shows them in `SessionsCard` in Réglages › Sécurité (« Déconnecter » on the other devices, `ReauthSheet` when the session is not fresh). **Cross-origin writes are refused** (#179, `common/http/same-origin.ts`, a Fastify `onRequest` hook registered in `main.ts`): `SameSite=Lax` still sends the cookies with a form post from a sibling subdomain, so a `POST`/`PUT`/`PATCH`/`DELETE` without `Authorization: Bearer` gets 403 (`Cross-origin request refused`) unless its `Origin` is the app origin (`APP_URL` or `WEBAUTHN_ORIGIN`) or its `Sec-Fetch-Site` is `same-origin` / `none`; without `Sec-Fetch-Site`, a foreign `Origin` is refused. Outside production only (#339), an `Origin` equal to the origin the request was addressed to (`X-Forwarded-Proto` + `X-Forwarded-Host` set by the web proxy, else `Host`) also passes: the phone opens the dev server at the Mac's LAN address over plain HTTP, where browsers send no `Sec-Fetch-*` and the `Origin` is not `APP_URL`. Requests with neither header (the web server's SSR and server-function calls, scripts) pass: never forward a browser's `Origin` from server-side code, and keep the `/api` proxy forwarding both headers unchanged. Use `@UseGuards(JwtGuard)` on every non-public route — `JwtGuard` verifies the cookie (or a personal access token, below) and attaches `{ sub: userId }` to `request.user`; read it with the `@CurrentUser()` decorator (`apps/api/src/auth/decorators/`).

## Passkeys (WebAuthn)

**Passkeys (WebAuthn)** (`apps/api/src/auth/passkeys/`, `@simplewebauthn/server` + `@simplewebauthn/browser`, web side in `lib/passkeys.ts`): discoverable credentials with user verification required, so sign-in needs no email. `POST /api/auth/passkeys/authentication/{options,verify}` are public and issue **the same session as a password login** (`createSession`, `setSessionCookies` in `auth/session-cookies.ts`: same cookies, rotation and reuse detection). Challenges live in `webauthn_challenges`: single use (deleted by the response that answers them, whatever the outcome), 5 minutes, purpose-bound (a registration challenge never signs in). `webauthn_credentials` keeps the credential id, public key (base64url), counter, transports, device type / backed up, an editable name and the last use; the API never returns or logs the credential id, public key or challenge, and library errors become fixed messages. The relying party is `WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGIN`, defaulting to `APP_URL`'s host name and origin (`env.webauthn`; the API refuses to boot when the RP id doesn't cover the origin). Listing, adding (`registration/{options,verify}`), renaming and revoking (delete) are session-only (`@TokenAccess('none')` on the controller). **Fresh session** (#176): adding or revoking a passkey, creating a personal access token and deleting the account (`DELETE /api/profile`) need a recent sign-in: the access JWT carries `auth_time` (last password or passkey sign-in, kept across refreshes in `refresh_tokens.authenticated_at`, read by `JwtGuard` into `request.user.authTime`) and must be under 5 minutes old (`FRESH_AUTH_MAX_AGE_SECONDS`), else 403 `Recent authentication required` (`FreshAuthGuard` / `assertFreshSession` in `auth/guards/fresh-auth.guard.ts`, after `JwtGuard`; put it on any new route that hands over or destroys the account). The web spots that 403 with `needsReauth` (`lib/reauth.ts`) and opens `ReauthSheet` (`components/auth/`), which asks for the password (`POST /api/auth/login`) or a passkey, then runs the action on a second button press (Safari needs a user gesture to create a passkey; a deletion stays an explicit choice). Throttles: options 10/min, verify 5/min per IP (`passkeyOptions`, `passkeyVerify`). On `/auth` (#543, the owner's « A · Carte de verre »: `AuthFrame` in `components/auth/`, a blurred blue light, the wordmark and one line, one glass card, shared by sign-up, forgotten password, reset and email check, one phone screen at 320×568) a Face ID « Se connecter » button (« Se connecter avec une passkey » for screen readers) comes first and « Mot de passe » opens the form in the same card; the form is server-rendered hidden (still a POST form with its submit disabled until hydration) and shown at once where WebAuthn is missing. The email field has `autocomplete="username webauthn"` and a background conditional-UI ceremony while the form is shown (cancelled on unmount; on the Face ID view nothing runs, so no error appears unasked); after a password sign-in, `PasskeyOffer` offers to add one when the account has none and the device has a platform authenticator ("Plus tard" snoozes it 30 days in `localStorage`). The password always stays: there is no passwordless account. Specs drive the real verification with a software authenticator (`passkeys/testing/soft-authenticator.ts`).

## Personal access tokens

**Personal access tokens** (`apps/api/src/auth/access-tokens/`, for the MCP server and scripts): created, listed and revoked in Réglages › Claude et accès (`/api/access-tokens`, session only), shown once, stored as a SHA-256 hash (`fin_pat_` + 43 base64url chars), scope `read` or `write`, optional expiry, last-use date, at most 20 active. `JwtGuard` accepts them as `Authorization: Bearer`; when that header is present the cookie is ignored. **Tokens are read-only and deny-by-default for writes**: GET/HEAD routes need `read`; any other method is refused to tokens unless the route declares `@TokenAccess('write')` (or `@TokenAccess('read')` for a POST that saves nothing, e.g. previews); `@TokenAccess('none')` locks a route to the session. Never put `@TokenAccess('write')` on deletes, account or auth changes, or imports other than the bank CSV preview and commit (#103); the routes open to tokens are the `TOKEN_MUTATING_ROUTES` allow-list of `app.routes.spec.ts`, which also names the ones the MCP write tools use (#77: manual transactions, `PATCH /transactions/:id` and `bulk-update`, rule create / preview / apply, `PUT /budgets/:categoryId`; #103: `POST /imports/preview` and `/imports/:id/commit`; #342: `POST /month-close/:month/close`; #358: `PUT /accounts/:id/invested-base` and its read-only preview; #413: `PUT /accounts/:id/positions/statements/:asOf` and its read-only preview; #357: `PUT /transactions/:id/splits`; #359: `POST /receivables`, `/receivables/debts`, `/receivables/payments`; #104: snapshots bulk, `POST|PUT /accounts/:id/holdings[/:holdingId]` for manual lines of manual-source crypto accounts only). Every token call is audited (`access_token_audit`: method, route pattern, status — never the URL, query, body, amounts or labels; kept 90 days) and token requests get their own rate-limit bucket keyed by the token hash (`access-token` throttler) on top of the per-IP one. HTTP specs that build `JwtGuard` use `JWT_GUARD_TEST_PROVIDERS` (`auth/guards/jwt-guard.testing.ts`).

## Remote MCP OAuth

**Remote MCP OAuth** (#78, [ADR 0003](../adr/0003-remote-mcp-oauth.md), runbook [`docs/runbooks/remote-mcp.md`](../runbooks/remote-mcp.md); **off by default**: the #102 audit passed and #328 ships the adapter's image and production service, turned on by the owner in the server's `.env`): an OAuth 2.1 authorization server in the API (`apps/api/src/auth/oauth/`) for the claude.ai / Claude app connectors, which reach the app only through the MCP adapter (`apps/mcp --http`). `REMOTE_MCP_ENABLED` (default off) is the kill switch: off, `RemoteMcpModule.register(false)` mounts no `/api/oauth` route and `OAuthService.authenticate` refuses every OAuth token; `REMOTE_MCP_PUBLIC_URL` is the adapter's public origin (issuer; the resource is `<origin>/mcp`), the consent page is `${APP_URL}/oauth/authorize` (web, tailnet, `routes/oauth.authorize.tsx`), `REMOTE_MCP_REDIRECT_URIS` the allow-list (default: the claude.ai and claude.com callbacks). Public RFC routes (`metadata`, DCR `register` for public clients only, `token`, `revoke`; RFC error bodies, throttled `oauthRegister` / `oauthToken`), owner routes session-only (`authorize` GET / POST / `deny`, `grants`, `audit`; approving needs a fresh session), `token-info` for the adapter (OAuth access tokens only). Code + PKCE S256 only, single-use 2-minute codes (a replayed code revokes its grant), access tokens 15 min, refresh tokens rotated with reuse detection (10 s grace for racing refreshes), grants at most 90 days, `resource` checked (RFC 8707). Tokens are `fin_oat_` / `fin_ort_` / `fin_oac_` (SHA-256 stored, never logged); scopes are the token scopes, and `JwtGuard` applies the same `@TokenAccess` rules to OAuth tokens as to personal access tokens (`request.accessToken.kind = 'oauth'`, `id` = the grant). Calls are audited in `oauth_audit` (`OAuthAuditHook`, same fields and retention as `access_token_audit`). The web lists grants with the tokens in « Accès actifs » and disconnects them from their detail (Claude et accès, #329; the connector choice is hidden when the API answers 404); `/auth?redirect=` returns only to the consent page (`lib/post-login.ts`). `app.routes.spec.ts` runs with it off; `auth/oauth/remote-mcp.module.spec.ts` audits these routes. The OpenAPI generator turns it on (`generate-spec-env.ts`) and runs under `tsx` without decorator metadata: declare query parameters with `@ApiQuery` and inject with explicit `@Inject(...)` where a constructor mixes tokens.

## SSR session renewal

**SSR session renewal**: `getMe` (`lib/auth.ts`) resolves the user with `resolveServerSession` (`lib/server-session.ts`): with a valid `token` it just calls `/api/auth/me`; when the access token is missing/expired and a `refresh_token` is present it calls `POST /api/auth/refresh` server-side, appends the rotated `Set-Cookie` headers to the page response, and makes later loaders in the same request use the new cookies. Refreshes are deduplicated per refresh token inside the web process (in-flight calls share one rotation, and a successful one is replayed for 10 s), and the proxied `POST /api/auth/refresh` goes through the same path, so concurrent reloads/tabs or a client refresh racing a reload never trip the API's reuse detection. This assumes a single web instance; the API's rotation and reuse detection are unchanged.
