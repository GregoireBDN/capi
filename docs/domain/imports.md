# Imports

Feature details moved out of [`CLAUDE.md`](../../CLAUDE.md) (#422). The domain rules, workflow conventions and architecture there apply here too.

## Formats

A bank file is read by a saved import profile, the CIC export's parser or the app's standard format, recognised from its header; an unknown file is mapped once on the Relevés page and saved as a profile (#431, [ADR 0007](../adr/0007-import-profiles.md)). The formats, the profiles and their rules: [`import-formats.md`](import-formats.md).

## The preview, line by line (#433)

Nothing is written before « Valider l’import »: a pending import changes nothing in the account. On the Relevés page (`components/import/`) the preview puts **what needs the owner first** (the « À faire d’abord » direction the owner chose on #433): four tiles count the lines À corriger (unreadable), À confirmer (probable duplicates), Nouvelles (will be imported) and Déjà là (already imported, left out); then numbered steps, each only when it has lines, numbered in order: **1 · Corriger** the unreadable lines, **2 · Confirmer** the probable duplicates (from another source, the file row next to the stored transaction, « C’est la même », the default, leaves it out and « Ce sont deux opérations » imports it, with its category), **3 · Vérifier** the new transactions (a compact list with date, category and amount). The lines already imported are folded into one row (« N lignes déjà dans vos opérations »); opened, each shows the stored transaction it matches and a link to it on Opérations (its month, account and label). The choices made (conflict decisions, categories) are kept by line number, so they survive the preview being checked again.

- **An unreadable line** is a card titled by one plain sentence naming the faulty value (`issueSentence` in `format.ts`: « La date 31/11/2026 n’existe pas. », « Débit -5,00 et crédit 5,00 sont remplis tous les deux : lequel garder ? »; the translated reason when there is no sentence for it or the line could not be split), its line number, and its form open below (the owner's direction D « Dans le formulaire »: no strip of cells above it). Under each field the file's value is shown (« Fichier : … », from `issues[].cells`, each with the field it holds; absent when an unclosed quote kept the line from being split, then a note says to type it from the file), the blamed one in red (« Dans le fichier : … », its input marked invalid until changed). The form starts from what could be read (`issues[].draft`: date, amount, label, balance, each null when unreadable): date, amount (signed with the « − » / « + » button), label, optional balance. « Vérifier » sends `PUT /api/imports/:id/lines/:lineNumber` (session only, never a token): the API checks the values (an existing calendar date, integer cents, a label of 1 to 500 characters after trimming) and **checks the whole preview again** with the account as it is now (dedupe with the occurrence index in file order, continuity, reconciliation with manual expenses, rules), then stores it with its new counts and period. The typed line moves to the step of its new status (new, to confirm or already imported); it is marked « Corrigée » (`rows[].fixedFrom`: the reason and cells it replaced) and can be typed again (« Modifier ») or put back as unreadable (« Ne pas importer », `DELETE /api/imports/:id/lines/:lineNumber`). A line left unreadable is not imported; the footer says how many stay aside.
- **Only unreadable lines can be typed**: a read row typed differently would get another dedupe hash, and re-importing the file would bring it back twice. A typed line is hashed like a read one, so re-importing the same file and typing the line the same way finds it already imported.
- **Changing the format**: a file read with a saved profile, while it is still in the page's memory (not an import resumed from the history), offers « Changer le format »: the mapping form opens on the saved profile, « Enregistrer et relire » changes it (`PUT /api/import-profiles/:id`, same rules as creating one) and reads the file again; the first pending import is dropped. A CIC or standard file has no format to change.
- **Privacy**: the cells and the draft hold the file's contents, like the rows: kept in the pending preview only, never in an issue's `message` (which names fields, never values) and never logged.

## Undoing a committed import

- **Undoing a committed import** (`DELETE /api/imports/:id`, #371, ADR 0005 R5, `imports/undo/`) deletes the rows it wrote with what was done on them by hand; re-importing the file brings back the bank rows, not the edits. `GET /api/imports/:id` gives a committed import's `undo`: `editedCount`, the rows edited by hand (filed by hand rather than by a rule, kind changed, one-off flag (these three not counted for a spreadsheet history import, whose rows come filed), note, split, correction, prepaid link, a transfer link that neither its rule nor matching would set again), the absorbed rows left out; and `absorbedManualCount`, the manual transactions its rows absorbed by reconciliation, which the undo puts back as manual transactions (`restoredManual` in its answer). The web reads it when « Annuler l’import » is pressed and says it in the confirmation (« 42 opérations … seront supprimées, dont 12 modifiées à la main et 3 rapprochées de vos saisies : ces 3 saisies seront remises comme saisies manuelles. Réimporter le fichier ne rendra pas les modifications. »), the plain sentence when both are 0.

## Reconciliation with manual transactions

- **Reconciliation** (`apps/api/src/imports/reconcile/`): a `new` import row with the same account and amount, booked at most 5 days from a manual transaction, replaces it on commit (one to one, closest first), keeping its category, kind, note (or typed label), one-off flag and split; the preview shows the match. The row keeps what it does not take over in `transactions.absorbed_manual` (the entry's own day, typed label and note, #371), so undoing the import puts the entry back as a manual transaction **on its own day**, with the row's current category, kind, flags, link, split and amount (the corrected day when the row's date was corrected; the note made from the label goes back to being the label), and re-importing the file reconciles it again. Unmatched manual transactions of the file's period (up to 5 days before its end) stay and are flagged for review. The commit re-matches against the manual transactions as they are then.

## Spreadsheet history import (one-shot)

The owner's pre-app history (a Google Sheet, ~3,250 categorized rows since 07/2023) is imported once from its CSV exports with `pnpm --filter @capi/api import:history` (code in `apps/api/src/imports/history/`, entry `apps/api/src/database/import-history.ts`; `node dist/database/import-history.js` where `tsx` is missing).

- **Dry run by default**: everything runs in one DB transaction that is rolled back unless `--commit` is passed. It prints counts only; `--report <path>` writes a detailed JSON report (merchant keys, line numbers, conflicts) and refuses any path inside the repo outside `data/`.
- **Inputs**: `Transactions` tab (`Date,Mois,Compte,Libellé,Montant (€),Catégorie,Groupe,Relevé,Ponctuel`, UTF-8, `,`-separated, `-1 234,56 €` amounts) and optionally the `Soldes` tab (`Fin de mois` + one column per account) → `balance_snapshots` on the last day of each month, upserted on (account, date). Columns are matched by name; bad rows are reported, never fatal.
- **Mapping** (`history/mapping.ts`): sheet category slugs → seeded slugs; a categorized row has its category's kind (#368; a row in `Revenu` filed under an expense category is a refund of it); without a category the kind comes from `Groupe` (`Mouvement` → transfer, `Revenu` → income, `Dépense` → expense). A `Groupe` / category disagreement where one side is a transfer (`transfer_kind_mismatch`) is filed without a category, with `Groupe`'s kind, in review. Unknown/ambiguous slugs (`paypal`, `virement_emis` outside `Mouvement`, ...) get no or a best-effort category and `needsReview = true`. Account codes `CC`/`LA`/`LJ` → Compte courant / Livret A / Livret Jeune (found by name or created, institution CIC); override with `--accounts <file.json>` and `--categories <file.json>`.
- **Dedupe**: same hashes as bank imports (`computeDedupeHashes`, `classifyRows`), so a re-run inserts nothing. Probable duplicates of rows from another source (CIC CSV) are conflicts: counted and **not inserted** unless `--include-conflicts` (then flagged for review). One `imports` row (`source = 'spreadsheet'`) per account that received rows.
- **Rules**: merchants seen ≥ 3 times and ≥ 90 % in one category and kind get a proposed `contains` rule on their merchant key (skipped when an existing rule already covers them or the pattern would also catch rows filed differently); created at the end of the rule order only with `--create-rules`.
